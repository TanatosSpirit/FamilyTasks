# FamilyTasks

**Спецификация приложения для Android**

Версия 1.0 · Июнь 2026

---

# 1. Обзор проекта

FamilyTasks — Android-приложение для совместного управления задачами между двумя устройствами в рамках одной семьи. Приложение работает полностью автономно, без серверов и облачных сервисов. Синхронизация происходит напрямую между устройствами через локальную WiFi-сеть.

**Целевая аудитория:** семья из 2+ человек, пользующихся двумя Android-устройствами в одной домашней сети.

**Ключевая идея:** каждое устройство является одновременно клиентом и сервером. Нет главного устройства, нет зависимости от интернета, нет сторонних сервисов.

## 1.1 Основные принципы

- **Без серверов** — приложение работает полностью офлайн
- **Без сторонних зависимостей** — только стандартный Android SDK и минимальные библиотеки
- **Симметричная архитектура** — оба устройства равноправны
- **Простота** — семейный инструмент, не корпоративный таск-трекер
- **Правило конфликтов:** побеждает последняя запись по времени (`updatedAt`)

# 3. Архитектура

## 3.1 Общая схема

Каждое устройство запускает два параллельных компонента: HTTP-сервер (NanoHTTPD на порту 8080) и UDP-listener (порт 9090). При появлении в WiFi-сети устройство рассылает UDP broadcast с своим `deviceId` и портом HTTP-сервера. Второе устройство получает broadcast, узнаёт IP собеседника и инициирует HTTP-синхронизацию.

## 3.2 Слои приложения

| **Слой** | **Классы / модули** | **Ответственность** |
|---|---|---|
| UI (Presentation) | Compose Screens, ViewModels | Отображение данных, обработка действий пользователя |
| Domain | UseCases, Repository interfaces | Бизнес-логика, правила мёржа |
| Data (Local) | Room DAO, TaskEntity | Локальное хранилище |
| Data (Sync) | SyncService, HttpServer, UdpDiscovery | Обнаружение устройств и синхронизация |
| Core | DeviceIdManager, NotificationScheduler | Утилиты, ID устройства, уведомления |

## 3.3 Протокол обнаружения устройств

Обнаружение происходит через UDP broadcast на адрес `255.255.255.255`, порт `9090`. Важно: Android требует разрешение `CHANGE_WIFI_MULTICAST_STATE` и активацию `MulticastLock`, иначе broadcast-пакеты фильтруются WiFi-чипом.

**Последовательность:**

1. Устройство A подключается к WiFi
2. A рассылает UDP broadcast: `{ deviceId: "aaa-111", httpPort: 8080 }`
3. Устройство B получает пакет, запоминает IP отправителя из заголовка сокета
4. B рассылает свой broadcast в ответ: `{ deviceId: "bbb-222", httpPort: 8080 }`
5. A получает broadcast B, запоминает его IP
6. Оба устройства знают IP друг друга — начинается HTTP-синхронизация

Broadcast повторяется каждые 30 секунд пока приложение активно, и однократно при каждом подключении к WiFi (`BroadcastReceiver` на `WIFI_STATE_CHANGED`).

## 3.4 HTTP API

Единственный эндпоинт: `POST /sync`

Запрос и ответ имеют одинаковую структуру — массив всех задач отправителя. Получатель применяет правило мёржа к каждой задаче и возвращает свои задачи. Таким образом один HTTP-запрос обеспечивает полный двусторонний обмен.

**Формат тела запроса/ответа:**

```json
{
  "deviceId": "aaa-111",
  "tasks": [
    {
      "id": "uuid",
      "title": "Купить молоко",
      "description": "2 литра, 3.2%",
      "assignedTo": "bbb-222",
      "status": "todo",
      "priority": "normal",
      "dueDate": 1718100000000,
      "createdBy": "aaa-111",
      "createdAt": 1718000000000,
      "updatedAt": 1718050000000,
      "deleted": false
    }
  ]
}
```

## 3.5 Правило мёржа

При получении задачи от собеседника:

- Если задача с таким `id` отсутствует локально — добавить
- Если задача присутствует — сравнить `updatedAt`: побеждает большее значение (Unix timestamp в миллисекундах)
- Если `updatedAt` одинаковый — оставить локальную версию (tie-break)

Удаление реализовано через tombstone: задачи физически не удаляются, устанавливается флаг `deleted: true` с обновлением `updatedAt`. UI фильтрует задачи с `deleted: true`. Это предотвращает «воскрешение» удалённых задач при синхронизации офлайн-устройства.

## 3.6 Офлайн-режим

Когда второе устройство недоступно, все изменения сохраняются локально в Room DB с актуальным `updatedAt`. При следующем подключении к сети запускается полная синхронизация — правило мёржа автоматически разрешит все расхождения. Специальная очередь изменений не нужна, так как при синхронизации передаётся весь массив задач целиком.

# 4. Модель данных

## 4.1 Задача (Task)

| **Поле** | **Тип** | **Описание** |
|---|---|---|
| id | String (UUID) | Уникальный идентификатор, генерируется при создании |
| title | String | Название задачи, обязательное поле, макс. 200 символов |
| description | String? | Подробное описание, опционально |
| assignedTo | String? | deviceId назначенного устройства, null = никому не назначено |
| status | Enum | `todo` │ `in_progress` │ `done` |
| priority | Enum | `low` │ `normal` │ `high` |
| dueDate | Long? | Срок выполнения, Unix timestamp мс, опционально |
| createdBy | String | deviceId создателя |
| createdAt | Long | Unix timestamp мс, не изменяется |
| updatedAt | Long | Unix timestamp мс, обновляется при каждом изменении |
| deleted | Boolean | Tombstone-флаг удаления, default: `false` |

## 4.2 Устройство / Пользователь (Device)

| **Поле** | **Тип** | **Описание** |
|---|---|---|
| deviceId | String (UUID) | Генерируется при первом запуске, хранится в SharedPreferences |
| displayName | String | Имя пользователя, задаётся при onboarding |
| color | Int | Цвет аватара, выбирается при onboarding |
| lastSeenAt | Long? | Последний раз онлайн, только локально |

Список известных устройств хранится локально. При первой синхронизации устройства обмениваются своими Device-профилями через дополнительное поле `devices` в теле `/sync`.

# 5. Онбординг и сопряжение устройств

## 5.1 Первый запуск

1. Приложение генерирует UUID и сохраняет как `deviceId` навсегда
2. Пользователь вводит своё имя (например, «Мама»)
3. Пользователь выбирает цвет своего аватара
4. Приложение показывает короткий код устройства (первые 8 символов UUID)
5. Пользователю предлагается два варианта: показать QR-код, или ввести код второго устройства вручную

## 5.2 Сопряжение

QR-код содержит JSON: `{ deviceId, displayName, color }`. Второе устройство сканирует QR и сохраняет профиль первого. После сопряжения приложение знает, чьи UDP broadcast-пакеты нужно обрабатывать — чужие (с неизвестным `deviceId`) игнорируются.

Сопряжение нужно выполнить только один раз. После этого обнаружение и синхронизация происходят автоматически при нахождении в одной WiFi-сети.

# 6. Функциональные требования

## 6.1 Управление задачами

- Создание задачи: название (обязательно), описание, приоритет, срок, назначение
- Редактирование любого поля задачи
- Смена статуса: `todo` → `in_progress` → `done` (и обратно)
- Удаление задачи (tombstone, физически не удаляется)
- Назначение задачи: себе, другому устройству, или никому

## 6.2 Просмотр и фильтрация

- Список всех активных задач (`deleted: false`)
- Фильтр по назначению: мои / чужие / все
- Фильтр по статусу: активные / выполненные
- Сортировка: по сроку, по приоритету, по дате создания
- Визуальное различие задач по цвету создателя/назначенного

## 6.3 Уведомления

- Уведомление о приближении срока: за 1 день и за 1 час (если задан `dueDate`)
- Уведомление при получении новой задачи, назначенной на тебя
- Уведомление при смене статуса задачи, созданной тобой
- Все уведомления настраиваются в настройках приложения

## 6.4 Синхронизация

- Автоматическая при появлении второго устройства в сети
- Ручная кнопка «Синхронизировать» в интерфейсе
- Индикатор статуса: онлайн / офлайн / последняя синхронизация N минут назад
- Синхронизация в фоне каждые 5 минут пока оба устройства в сети (WorkManager)

# 7. Пользовательские сценарии

## Сценарий 1: создание и назначение задачи

Мама открывает приложение, нажимает «+», вводит «Забрать ребёнка из школы», назначает Папе, ставит срок на 15:00. Нажимает сохранить. Задача появляется у Папы при следующей синхронизации (автоматически, как только оба телефона в одной сети). Папа получает уведомление «Тебе назначена задача».

## Сценарий 2: офлайн-работа

Папа уходит из дома. Дома меняет задачу Мама, на улице — Папа. Когда Папа возвращается домой и подключается к WiFi, происходит синхронизация. Побеждает та версия задачи, которую изменили позже по времени. Пользователи не видят никакого конфликта — всё происходит прозрачно.

## Сценарий 3: выполнение задачи

Папа выполнил задачу, меняет статус на «Готово». При синхронизации Мама видит задачу в разделе выполненных. Если задачу создавала Мама, она получает уведомление о выполнении.

# 11. Ограничения и известные сложности

## 11.1 Конфликты

Правило «последняя запись побеждает» означает, что если оба пользователя одновременно редактировали одну задачу офлайн, одно из изменений будет потеряно молча. Для семейного приложения с двумя пользователями это приемлемо. Если потребуется более сложная логика — необходим vector clock, что существенно усложняет реализацию.

## 11.2 UDP broadcast и корпоративные сети

На некоторых WiFi-роутерах или в корпоративных сетях UDP broadcast может быть заблокирован. Для домашней сети это не актуально. В качестве fallback можно добавить ручной ввод IP второго устройства в настройках.

## 11.3 Масштабирование

Архитектура рассчитана на два устройства. Добавление третьего устройства потребует изменения логики sync (каждое устройство должно синхронизироваться с каждым) и UI сопряжения. Это не предусмотрено текущей спецификацией.

## 11.4 Фоновая работа на Android

Android агрессивно убивает фоновые процессы для экономии батареи. HTTP-сервер должен работать как Foreground Service с постоянным уведомлением, иначе ОС его остановит. Это стандартная практика для приложений с сетевой активностью.
