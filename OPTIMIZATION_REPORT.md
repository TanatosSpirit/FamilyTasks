# FamilyTasks — отчёт по оптимизации и архитектуре

**Дата:** 2026-06-09
**Область:** энергопотребление, производительность, аллокации памяти, размер сборки, архитектурные костыли.
**Контекст:** приложение для двух устройств в одной WiFi-сети, полностью офлайн. Фоновый Foreground Service держит UDP-листенер + HTTP-сервер живыми постоянно — поэтому **главный ресурс под угрозой это батарея и WiFi-радио**, а не CPU UI.

Находки отсортированы по реальному влиянию на потребление ресурсов.

---

## 🔴 Критично (батарея / радио)

### B1. MulticastLock удерживается весь жизненный цикл сервиса
`UdpDiscovery.kt:71-78` — `acquireLock()` вызывается в `start()`, а `releaseLock()` только в `stop()` (т.е. при смерти сервиса). Лок **не отпускается** ни когда партнёр найден (`pauseDiscovery`), ни во время длинных пауз backoff (5 → 15 минут).

`MulticastLock` запрещает WiFi-чипу уходить в power-save — это самая дорогая по заряду операция во всём приложении, и она активна 24/7.

**Что сделать:**
- Лок нужен только пока листенер реально должен слышать чужие broadcast'ы. Рассмотреть удержание лока **только на время burst-фазы**, отпуская его на время паузы backoff (`startBurst`: acquire перед `repeat`, release перед `delay(pause)`). Минус — в паузу не услышим спонтанный broadcast партнёра; плюс — радио спит большую часть времени.
- Как минимум: измерить через уже встроенное логирование `MulticastLock acquired/released` сколько лок реально держится, и задокументировать сознательный компромисс.
- Уточнить: используется именно **broadcast** `255.255.255.255`, а не multicast. На многих устройствах для приёма broadcast лок не обязателен — стоит проверить на целевом железе, возможно лок не нужен вовсе.

### B2. Release-сборка без R8/минификации
`app/build.gradle.kts:24-25` — `isMinifyEnabled = false`. Нет shrinking кода, нет dead-code elimination, нет `shrinkResources`. Следствия:
- APK заметно больше → дольше старт, больше I/O.
- **Логирующий код (см. B3) не вырезается** в проде.
- Нет оптимизаций proguard-android-**optimize** (он подключён, но не работает без minify).

**Что сделать:** включить `isMinifyEnabled = true` + `isShrinkResources = true` для release, добавить keep-правила для kotlinx.serialization (`@Serializable` DTO), NanoHTTPD, Room, Hilt. Это разовая настройка с большим эффектом.

### B3. AppLogger активен в release и аллоцирует O(n) на каждую запись
`AppLogger.kt:30-37` — каждый вызов `d/i/w/e`:
1. пишет в Logcat (`Log.*`) **даже в release**;
2. внутри `synchronized` делает `buffer.toList()` — копия до 500 элементов **на каждую запись лога**;
3. публикует новый список в `StateFlow` даже если на него никто не подписан.

Sync-путь логирует ~10–15 раз за цикл (broadcast, merge, sync OK/fail). На каждый лог создаётся свежий список из сотен `LogEntry`. Это постоянное давление на GC и расход CPU на фоне, где приложение должно «спать».

**Что сделать:**
- Обернуть запись в буфер/Logcat в `if (BuildConfig.DEBUG)` либо вынести `Log.*` под флаг.
- Не пересобирать список на каждый `append`: хранить `StateFlow<ArrayDeque>` и эмитить снапшот лениво (например, только когда экран логов реально подписан), либо публиковать через `conflate`/throttle.
- Понизить уровень болтливых `d`-логов в горячем пути (каждый отправленный UDP-пакет логируется отдельно — `UdpDiscovery.kt:152`).

## 🟠 Средне (БД, лишняя работа, петли)

### M1. MergeTasksUseCase перезаписывает всю таблицу задач при каждом sync
`MergeTasksUseCase.kt:52-53` — `upsertTasks(merged)` пишет **весь** список задач, включая неизменённые. Последствия:
- Полная перезапись таблицы на каждый sync (лишний disk I/O).
- Room инвалидирует таблицу → `observeAllTasks()` переэмитит → `observeTaskChanges()` (`SyncService.kt:144-152`) с `debounce(3s)` может **снова дёрнуть `triggerSync()`** → потенциальный ping-pong синхронизаций между устройствами, пока `updatedAt` не стабилизируется. Спасает только `distinctUntilChanged`, но он сравнивает весь список (O(n)).

**Что сделать:** собрать список **только добавленных/обновлённых** задач и писать `upsertTasks(changed)`. Если `changed.isEmpty()` — не трогать БД вообще. Это убирает и лишние записи, и самоиндуцированные триггеры.

### M2. Единый combine пересортировывает весь список при каждом изменении syncState
`TaskListViewModel.kt:112-159` — `tasks`, `devices`, `filters` и `syncStatus` слиты в **один** `combine`. Любая смена `syncState` (`SYNCING → SUCCESS → IDLE` — несколько раз за каждый sync) запускает заново **полный `filter + sortedWith`** всего списка задач. И всё это на диспетчере коллектора (Main, без `flowOn`).

**Что сделать:**
- Разделить: один flow выводит отфильтрованный/отсортированный список (`tasks × devices × filters`) с `.flowOn(Dispatchers.Default)`; внешний `combine` подмешивает только `syncStatus` в финальный `UiState`. Тогда смена статуса sync не пересортировывает задачи.
- Сортировку/фильтрацию увести с Main-потока.

### M3. Двойной независимый мониторинг сети
- `SyncService.kt:51-73` слушает **deprecated** `WifiManager.NETWORK_STATE_CHANGED_ACTION` через `BroadcastReceiver`.
- `TaskListViewModel.kt:76-97` параллельно использует `ConnectivityManager.NetworkCallback`.

Два разных механизма для одного факта «есть ли WiFi», один из них на устаревшем API. Лишние коллбэки и расхождение состояний.

**Что сделать:** один `NetworkCallback` в сервисе, состояние WiFi публиковать через `SyncManager` (`StateFlow<Boolean>`), ViewModel читает оттуда. Убирает дубликат и deprecated-путь.

### M4. UdpDiscovery создаёт новый сокет и резолвит адрес на каждый пакет
`UdpDiscovery.kt:143-156` — `sendBroadcast()` на **каждый** пакет: `InetAddress.getByName("255.255.255.255")` + `DatagramSocket().use{}` (открыть/настроить/закрыть). В burst'е это 5 раз подряд, плюс ответные broadcast'ы из листенера.

**Что сделать:** закешировать `InetAddress` (константа, резолв тривиальный, но всё же) и переиспользовать один отправляющий `DatagramSocket` на время жизни discovery вместо open/close на каждый пакет.

## 🟡 Низко (рост со временем, мелочи)

### L1. Tombstone'ы накапливаются вечно и таскаются везде
Физического удаления нет (`deleteTask` → `deleted = true`). Следствия со временем:
- `getAllTasksSnapshot()` (`TaskRepositoryImpl.kt:34`) включает удалённые → **каждый sync шлёт по сети все когда-либо удалённые задачи** (`SyncService.kt:167`, payload растёт безгранично).
- `TaskListViewModel` берёт `observeAllTasks()` и фильтрует `!it.deleted` в памяти (`TaskListViewModel.kt:113,120`), хотя в DAO уже есть индексируемый `observeActiveTasks()` (`TaskDao.kt:10`), который **не используется**.

**Что сделать:**
- В UI переключиться на `observeActiveTasks()` (БД не отдаёт tombstone'ы).
- Добавить периодическую очистку tombstone'ов старше N дней (после того как оба устройства гарантированно их увидели).
- Опционально: дельта-sync (слать только задачи с `updatedAt > lastSyncWithPeer`) вместо полного снапшота.

### L2. Отдельные инстансы Json в трёх местах
`HttpServer.kt:15`, `HttpClient.kt:28`, `UdpDiscovery.kt:35` — по своему `Json { ignoreUnknownKeys = true }`. Мелочь, но логично вынести один общий синглтон (конфиг идентичен).

### L3. SharedPreferences читается внутри combine-трансформа
`TaskListViewModel.kt:156-157` — `prefs.displayName` и `prefs.pairedDeviceId` читаются на **каждую** эмиссию UiState. Дёшево (in-memory map), но при частых пересчётах (см. M2) лишнее. Лучше держать `displayName` как `StateFlow`.

### L4. DueNotificationWorker: id уведомления = currentTimeMillis().toInt()
`DueNotificationWorker.kt:29` — `System.currentTimeMillis().toInt()` обрезает long → возможны коллизии id уведомлений. Корректность, не производительность, но стоит заменить на стабильный id из `task.id.hashCode()`.

### L5. HttpServer.runBlocking блокирует поток NanoHTTPD
`HttpServer.kt:29` — `runBlocking { onSyncRequest() }` держит worker-поток NanoHTTPD на всё время merge + запись в БД. Для протокола из одного эндпоинта приемлемо, но это блокирующий мост корутина→поток; при желании можно перевести на асинхронную обработку.

## 🧱 Архитектурные расхождения

### A1. Документированный SyncWorker / периодический WorkManager-фолбэк не реализован
`CLAUDE.md` и спецификации (`sync_*.md`) описывают «резервный триггер — WorkManager каждые 5 мин» и `SyncWorker`. В коде (`grep` по `*.kt`) **их нет** — есть только `DueNotificationWorker`. То есть единственный путь восстановления после долгого backoff (15 мин) или потерянного UDP-пакета — переподключение WiFi. Либо реализовать периодический фолбэк, либо убрать упоминания из доков, чтобы не вводить в заблуждение.

### A2. Заглушка Device при обнаружении пира
`SyncService.kt:135` — при первом обнаружении создаётся `Device(displayName = "", color = 0)`. До первого успешного sync партнёр в UI без имени/цвета. Поведение задокументировано (`onPeerDiscovered` не перетирает существующие данные), но стоит держать в уме как намеренный костыль.
