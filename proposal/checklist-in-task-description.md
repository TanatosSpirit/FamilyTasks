# Предложение: чек-лист внутри задачи (сборы, покупки и т.п.)

## Контекст

Для задач вроде «Собрать чемодан» или «Список покупок» одного текстового `description` мало — нужны отдельные пункты, которые можно отмечать по одному, ничего не теряя из виду. Открытый вопрос: как ввод такого списка сделать удобным для обычного пользователя, без знания синтаксиса (markdown `- [ ]` с превью явно не годится — лишний шаг и незнакомый синтаксис).

Второе, менее очевидное ограничение: sync-протокол приложения работает на **whole-task LWW** — конфликты разрешаются побеждающим `updatedAt` всей задачи (`MergeTasksUseCase`), а не по отдельным полям. Любой формат чек-листа должен укладываться в эту модель без переделки протокола.

## Модель данных — независимо от варианта UI

Вариант А, разобранный и отклонённый: отдельная таблица `checklist_items(id, taskId, text, checked, order)`, аналог `task_sync_state`. Требует per-item merge (какой пункт новее, какой удалён, tombstone на пункт) — фактически второй протокол синхронизации поверх первого. Не согласуется с текущей архитектурой (везде on-task granularity) и сильно увеличивает объём работы ради фичи, которая по сути — список строк с галочкой.

Вариант Б (рекомендуется): чек-лист — **одно сериализованное поле на `Task`**, по образцу `repeatRule` (строка, `serialize()`/`deserialize()`, участвует в обычном whole-task LWW). Например:

```
checklistItems: String   // JSON: [{"text":"Паспорт","checked":true},{"text":"Зарядка","checked":false}]
```

Такое поле:
- участвует в существующем merge как часть задачи — ничего не меняется в `MergeTasksUseCase`, `SyncDto`, файловом экспорте;
- требует одну Room-миграцию (v5 → v6), аналогичную `MIGRATION_3_4`;
- конфликт «оба отметили разные пункты офлайн» разрешается так же грубо, как сейчас разрешается конфликт по `title` — целиком в пользу более позднего `updatedAt`. Это то же самое ограничение, что уже описано в «Известных ограничениях» (last-write-wins), не новое поведение.

Дальше — варианты именно UI ввода/отображения поверх этого поля.

## Вариант 1 — отдельная секция «Чек-лист» с интерактивными строками (рекомендуется)

Под полем «Описание» — блок: список строк `[чекбокс] [текстовое поле] [✕ удалить]`, снизу «+ Добавить пункт». Enter в текстовом поле пункта создаёт следующую пустую строку и сразу фокусирует её (как в Google Keep / Reminders / Todoist). В `TaskDetailScreen` те же строки становятся кликабельными чекбоксами без режима редактирования.

**Плюсы**
- Ноль синтаксиса — пользователь работает с чекбоксами и текстовыми полями, ничего не «переключает» на превью.
- Знакомый паттерн (Google Keep, Apple Reminders, Todoist) — не нужно объяснять, как пользоваться.
- Отметка пункта готовым — один тап, без входа в режим редактирования задачи.

**Минусы**
- Больше нового UI-кода: `ChecklistItemRow`, управление фокусом при добавлении/Enter, drag-to-reorder (если нужен) — не «одно текстовое поле».
- `TaskFormFields`/`EditTaskContent`/`CreateTaskScreen`/`TaskDetailScreen` — четыре места, куда встраивается блок.
- Нужно решить: чек-лист — это отдельная опция («добавить чек-лист» кнопкой) или всегда видимый пустой блок с одной строкой-заглушкой. Первое чище для задач без чек-листа (большинство).

## Вариант 2 — «умный» многострочный текст

Отдельное многострочное поле «Пункты» (или спецрежим `description`): пользователь печатает по одному пункту на строку без всякого синтаксиса. При сохранении каждая непустая строка становится пунктом чек-листа с `checked = false`. Отображение — как в варианте 1 (интерактивные чекбоксы), но **ввод** — обычный textarea.

**Плюсы**
- Минимальный новый UI при вводе — одно `OutlinedTextField(singleLine = false)`, никакой логики строк/фокуса/кнопок добавления.
- Быстрый массовый ввод (вставить список из буфера обмена — сразу N пунктов).

**Минусы**
- Нельзя отметить пункт готовым прямо во время печати списка — только после сохранения, при повторном открытии/на детальном экране. Слабее «живого» ощущения для сценария «собираю чемодан прямо сейчас, отмечаю по ходу».
- Редактирование существующего чек-листа (добавить один пункт в середину, поправить опечатку) неудобнее — либо снова через textarea (перезаписывая checked-состояния из текста), либо два разных режима редактирования (textarea для добавления + чекбоксы для отметки), что путает.

## Вариант 3 — вариант 1 с шаблонами

То же, что вариант 1, плюс кнопка «Вставить шаблон» с готовыми наборами («Чемодан», «Продукты») — заполняет пункты одним тапом, дальше редактируются как обычные строки.

**Плюсы**
- Решает самый частый кейс («собрать чемодан») в один тап, без набора текста вообще.
- Не требует нового формата данных — шаблоны это просто константы, разворачивающиеся в тот же список строк варианта 1.

**Минусы**
- Дополнительный экран/диалог выбора шаблона + хранение самих шаблонов (constants или, если нужно кастомизировать, — ещё один слой хранения).
- Может быть избыточным на первую итерацию — легко добавить поверх варианта 1 позже, без переделок.

## Рекомендация

**Вариант 1** как база — он ближе всего к тому, что пользователи уже знают из других чек-лист-приложений, и не жертвует «отметить пункт сразу же», что для сценария «собираю чемодан» — главная ценность фичи. **Вариант 3** — естественное расширение поверх него, стоит рассмотреть отдельным шагом после того, как база обкатана. **Вариант 2** имеет смысл только если приоритет — скорость первого ввода длинного списка (вставка из буфера), а не последующая работа с ним.

Независимо от выбора UI-варианта — данные храним как единое сериализованное поле на `Task` (не отдельную таблицу), чтобы не трогать sync-протокол.

## Открытые вопросы (для следующего обсуждения)

- Чек-лист — это замена `description` для таких задач, или отдельное поле рядом с ним (задача может иметь и текст, и список)?
- Нужен ли drag-to-reorder пунктов в первой версии, или порядок ввода фиксирован?
- Показывать ли прогресс («3 из 7») в карточке списка задач — потребует лёгкого парсинга JSON в `TaskListScreen` для каждой карточки.
- Как влияет на `isSecret`: чек-лист внутри секретной задачи — секретен целиком (наследует правило `isSecret` — никогда не покидает устройство), отдельного решения не требует, но стоит явно проговорить при реализации.

## Оценка объёма (ориентировочно, для варианта 1)

Room-миграция (v5 → v6, новая колонка `checklistItems`), extension-функции сериализации по образцу `Recurrence`, новый composable `ChecklistSection` + `ChecklistItemRow`, встраивание в `CreateTaskScreen`/`EditTaskContent`/`TaskDetailScreen`, отображение в `TaskListScreen` (опционально, прогресс). День-полтора работы с ручной проверкой на устройстве.
