# Предложение: стратегия гашения индикатора pending-sync (файловый обмен)

## Контекст

Индикатор pending-sync (приглушённая карточка + значок `Sync`) показывает задачи, которых партнёр ещё не получил. Флаг вычисляется сравнением `task.updatedAt` с watermark-ом подтверждённой синхронизации.

Изначально был один watermark — `lastConfirmedSyncTimestamp` (LCT), он же боевой watermark **delta-sync** (`docs/delta-sync.md`): `SyncService.triggerSync()` шлёт по WiFi только задачи с `updatedAt > LCT`.

Коммит «file sync and sync indicator» (`15426e1`) заставил файловый импорт (`ExportImportManager`) двигать LCT, чтобы индикатор гас и после файлового обмена. Это создало проблему: файловый снимок партнёра **не атомарен**, а LCT — контиг­уозный watermark. `max(updatedAt моих задач в файле)` мог перескочить через недоставленную задачу (например, партнёр поднял `updatedAt` другой моей задачи, отметив её «Готово»).

Последующий фикс развязал watermark-и: файловое подтверждение вынесено в отдельные индикаторные поля (`lastOwnFileConfirmedTimestamp`, `lastPartnerFileTimestamp`), а LCT снова двигает **только** WiFi. Этот фикс сейчас в рабочем дереве.

## Что важно зафиксировать по итогам разбора

1. **Потери данных нет ни в одном варианте.** Разбор показал: состояние «оба watermark-а перескочили `t3`, а задача не доставлена» структурно недостижимо. Любой путь, поднимающий watermark партнёра выше `t3`, по построению доставляет задачу (файловый экспорт всегда полный снимок; WiFi-responder отдаёт всё `> sinceTimestamp`). WiFi всё выравнивает.
2. **Проблема исходного бага была двойной, но серьёзная часть мнимая:**
   - реальная — **косметика**: индикатор мог ложно погаснуть;
   - мнимая — «тихая потеря данных»: на деле самовосстанавливается на первой WiFi-встрече (симметричная дельта responder-а).
3. **Файловое подтверждение — точное, а не оптимистичное.** `lastOwnFileConfirmedTimestamp` поднимается не когда «я отправил файл», а когда **моя задача вернулась в файле партнёра** — то есть партнёр её импортировал, экспортировал, и я импортировал обратно. Это настоящий round-trip по файлам, твёрдое доказательство доставки.

Таким образом, выбор — **чисто про UX индикатора**, а не про корректность данных.

## Вариант A — оставить текущий фикс (три watermark-а)

Файловый импорт двигает два отдельных индикаторных поля; LCT — только WiFi. Порог зависит от `createdBy`:
- моя задача → `max(lastConfirmedSyncTimestamp, lastOwnFileConfirmedTimestamp)`;
- задача партнёра → `max(lastConfirmedSyncTimestamp, lastPartnerFileTimestamp)`.

**Плюсы**
- Индикатор **точен и в WiFi-, и в remote-режиме** — гаснет после реального файлового round-trip.
- Данные безопасны, delta-watermark чист.
- Уже реализовано и протестировано пользователем.

**Минусы**
- **Три поля состояния + ветка `createdBy`** — самый «толстый» вариант по состоянию.
- Остаётся **редкая косметическая неточность**: ложное гашение, когда партнёр поднял `updatedAt` другой моей задачи выше недоставленной (max-overshoot по индикаторному полю). Безвредно для данных.

**Когда выбирать:** партнёры регулярно подолгу в разных сетях, файл — значимый канал, и важно, чтобы индикатор отражал файловые доставки.

## Вариант B — watermark только по WiFi, файл только мёржит

Убрать всю файловую watermark-логику (и оба индикаторных поля, и ветку `createdBy`). `ExportImportManager.importFromUri` только вызывает `mergeAll`. Индикатор: `task.updatedAt > lastConfirmedSyncTimestamp` — один watermark, семантика «подтверждено по надёжному WiFi-каналу».

**Плюсы**
- **Самый простой** вариант: одно поле, минус два поля и ветка относительно текущего.
- Данные безопасны, LCT идеально соответствует своему смыслу.
- Исходный баг невозможен по построению.
- Честная семантика: «ещё не подтверждено по надёжному двунаправленному каналу».

**Минусы**
- В remote-режиме **индикатор висит подсвеченным** до WiFi-встречи, хотя файл задачу доставил. Для тех, кто живёт на файлах, индикатор становится шумным.
- **Эффект «наизнанку» на принимающем устройстве:** импортированная задача партнёра сразу показывается «ждёт синхронизации», хотя у создателя она есть. Самоисправляется по WiFi.
- Выбрасывает **точное** файловое подтверждение (см. пункт 3 выше) ради простоты.

**Когда выбирать:** устройства почти всегда в одном WiFi (что соответствует архитектуре — приложение «в одной WiFi-сети»), файл — редкий запасной канал в отъезде. Тогда подсветка во время отъезда честна и сама гаснет дома.

## Вариант C — компромисс (только `lastPartnerFileTimestamp`)

Оставить одно индикаторное поле — `lastPartnerFileTimestamp` (гасит задачи **партнёра** при импорте), а **свои** задачи гасить только по WiFi. `lastOwnFileConfirmedTimestamp` убрать.

**Плюсы**
- Убирает самый странный эффект B — «наизнанку» на принимающем устройстве (импортированная задача партнёра сразу гаснет).
- Проще варианта A (два поля вместо трёх, к delta-watermark отношения не имеет).
- Данные безопасны.

**Минусы**
- **Асимметрия:** задачи партнёра гаснут по файлу, а мои — нет. Мои файловые доставки всё равно висят до WiFi.
- Промежуточная сложность — надо объяснять, почему стороны обрабатываются по-разному.

**Когда выбирать:** хочется убрать самую заметную странность B, но не тащить полный учёт своих файловых подтверждений.

## Вариант D — per-task трекинг

Заменить скалярные watermark-и точным per-task признаком «партнёр подтвердил эту версию задачи». Отдельная таблица `task_sync_state(taskId, confirmedUpdatedAt)`; индикатор — `task.updatedAt > confirmed[task.id]`. Подтверждение пишется при любом входящем payload по правилу «local.updatedAt <= partner.updatedAt».

**Плюсы**
- **Точен во всех режимах**, включая edge-case с max-overshoot — косметика чинится полностью.
- **Поглощает** оба индикаторных watermark-а и ветку `createdBy` — чистая замена, не «фича поверх фичи».
- Единая симметричная формула.

**Минусы**
- **+1 миграция БД** (v4 → v5) — основная цена, ради чисто косметической точности.
- Больше кода: сущность, DAO, 4 точки подтверждения (WiFi-initiator success, WiFi-responder, file import), очистка строк при purge/unpair.
- Карта `confirmed` эмитит на каждый синк → рекомпозиция списка (дёшево: реактивно на уже происходящий синк, без новых пробуждений — энергомодель не меняется).

**Когда выбирать:** индикатор считается важной фичей, remote-режим используется активно, и точность оправдывает миграцию БД.

## Ключевой вопрос для выбора

**Как часто два устройства подолгу НЕ в одной WiFi-сети?**

- Почти всегда дома в одном WiFi, файл — редкий фолбэк → **B** (или **C**, если мешает эффект «наизнанку»). Архитектура приложения склоняет сюда.
- Регулярно подолгу в разных сетях, файл — основной канал → **A** или **D**.

## Рекомендация

По умолчанию — **вариант B**: он проще всех, безопасен, семантически честен и соответствует тому, что приложение спроектировано под одну WiFi-сеть. **D** оправдан только если индикатор станет ключевой фичей для remote-пользователей — тогда миграция окупается. **A** — разумно «оставить как есть», если не хочется трогать уже работающий код. **C** — если конкретно эффект «наизнанку» на импорте раздражает, а остальное в B устраивает.

## Оценка объёма

- **B:** удаление ~2 полей + ветки, правка `ExportImportManager`, `TaskListViewModel`, `TaskListScreen`, доков. Полчаса.
- **C:** как B, но оставить `lastPartnerFileTimestamp`. Полчаса.
- **A:** ноль (уже реализовано).
- **D:** новая таблица + DAO + миграция + 4 точки подтверждения + очистка + правка UI + тесты + доки. Существенно больше, отдельным коммитом.


## Эксперимент
Вот точный, детерминированный сценарий. Он гарантированно показывает баг в видимой форме (индикатор гаснет на задаче,
  которой у партнёра нет), без зависимости от гонок.

  Подготовка

  - Устройства сопряжены, но во время теста НЕ в одной WiFi-сети (например, B на мобильном интернете). Это важно: иначе
  WiFi-sync сам доставит задачу и замаскирует баг. Файлы передаём через мессенджер/почту.
  - Пусть A = моё устройство («Мама»), B = партнёр («Папа»).
  - Все задачи — не секретные.

  Шаги

  Что произойдёт на шаге 7 (баг)

  При импорте ExportImportManager.kt:82-85:
  - myTasksInFile = {M1@t_done, M2@t2}, maxOwnUpdatedAt = t_done.
  - lastConfirmedSyncTimestamp := t_done.

  Порог для M3 (createdBy == моё) = LCT = t_done. А updatedAt(M3) = t3 < t_done → isPendingSync = false.

  Результат: на A карточка M3 «Позвонить врачу» становится обычной — индикатор синка пропадает, как будто задача
  доставлена.

  Доказательство, что это баг

  Откройте список задач на B — задачи «Позвонить врачу» там нет и никогда не было. То есть A показывает M3 как
  синхронизированную, хотя партнёр её не получал. Замок watermark-а перескочил через M3 из-за того, что партнёр поднял
  updatedAt другой моей задачи (M1) завершением — а это бытовое, частое действие.

  Как доходит до реальной потери данных (а не только индикатора)

  Файловый экспорт всегда полный (sinceTimestamp = 0), поэтому по файлу M3 в итоге уедет. Тихая потеря — на WiFi-дельте:  после шага 7 LCT = t_done, и triggerSync() на A как инициаторе отправит только updatedAt > t_done → M3 (t3)
  пропущена.

  Чтобы увидеть это вживую на шаге 8: сведите A и B в одну WiFi-сеть.
  - Если у B watermark < t3 (обычный случай, B своих задач не подтверждал) — симметричная дельta responder-а на стороне
  A отдаст M3 при синке, инициированном B, и баг замаскируется (M3 всё-таки приедет). Это и есть та частичная защита, о
  которой я писал.
  - Чтобы потеря стала наблюдаемой, watermark B тоже должен быть > t3. Это достижимо (B создаёт свою задачу и получает
  её подтверждение через файл от A до шага 8), но требует ещё пары round-trip'ов.

  Поэтому для двух устройств самый чистый и гарантированный способ увидеть дефект — шаги 1-7 и сравнить экран A с
  экраном B: индикатор на A говорит «синхронизировано», B задачу не видел. Это и есть корень — ложное состояние
  watermark-а; WiFi-стопор лишь его следствие.
