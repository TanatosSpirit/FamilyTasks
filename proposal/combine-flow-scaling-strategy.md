# Предложение: стратегия масштабирования `combine`-конвейера в `TaskListViewModel`

## Контекст

`kotlinx.coroutines.flow.combine` имеет типизированные перегрузки только до **5** потоков (`combine(f1..f5) { a,b,c,d,e -> }`). Дальше — только vararg-вариант `combine(vararg flows: Flow<T>) { array: Array<T> -> }`, где типы стираются в `Array<Any?>` и требуют ручных касто́в.

Проект уже упирался в этот потолок и обходил его группировкой родственных потоков в промежуточные data-классы: `Filters`, `Triple` (`syncTimestamps`), `SyncStatus`. После добавления тумблера `showPendingSyncIndicator` (см. `docs/pending-sync-indicator.md`) состояние `TaskListViewModel.kt` такое:

| Combine | Потоков | Запас |
|---|---|---|
| `filters` (:112) | 4 | 1 |
| `syncTimestamps` (:116) | 3 | 2 |
| `syncStatus` (:122) | 5 | **0 — потолок** |
| `uiState` (:132) | 5 | **0 — потолок** |

Два из четырёх узлов конвейера уже на потолке. Следующий новый источник состояния (ещё один тумблер настроек, ещё один флаг синхронизации) не влезет напрямую и потребует решения архитектурного вопроса — как расширяться дальше.

## Что важно зафиксировать

1. **Ограничение — только на один вызов `combine`, не на систему в целом.** Вложенность (`combine` из результатов других `combine`) может идти сколь угодно глубоко. Упираться в 5/5 на конкретном узле — ожидаемая, а не аварийная ситуация.
2. **Два узла на потолке требуют разного решения.** `syncStatus` группирует сущностно близкие потоки (состояние синхронизации) — расширять его нужно новым слоем группировки внутри той же темы. `uiState` — конечная точка, куда сходится всё для UI — расширять его означает либо новый слой группировки, либо отказ от единого объекта состояния.
3. **Куда допишется следующий тумблер настроек, зависит от выбранного варианта ниже.** Кандидат вроде ещё одного preference-флага (`hideSecretTasksFlow`-подобного) логически ближе к `filters`, но `filters` не то место, куда стекаются toggle-и, не влияющие на фильтрацию списка (как `showPendingSyncIndicator`) — сейчас он подключён отдельным потоком прямо к `uiState`, что и съело последний слот.

## Вариант A — продолжать вкладывать (углублять существующий паттерн)

При следующем переполнении вводить ещё один промежуточный data-класс, группируя по смыслу. Например: `Toggles(hideSecretTasks, showPendingSyncIndicator, ...)` вместо того, чтобы `showPendingSyncIndicator` был отдельным аргументом `uiState`; тогда у `uiState` снова появляется свободный слот.

**Плюсы**
- Ничего нового не изучать — уже устоявшийся в проекте паттерн (`Filters`, `SyncStatus`).
- Полная типобезопасность, без кастов.
- Глубина вложенности не ограничена — масштабируется неограниченно долго.

**Минусы**
- Каждое новое переполнение — это ручное решение, куда именно группировать (нет автоматического правила).
- С ростом дерева усложняется чтение: чтобы понять, откуда взялось поле в `TaskListUiState`, надо пройти 2-3 уровня `combine`.

**Когда выбирать:** сейчас, по умолчанию — экран один, полей ещё разумное количество, рефакторинг всего конвейера не оправдан.

## Вариант B — расщепить `TaskListUiState` на несколько независимых `StateFlow`

Вместо одного объединённого объекта — несколько тематических `StateFlow` в `TaskListViewModel` (например, `taskListState`, `syncStatusState`, `toggleState`), которые `TaskListScreen.kt` читает отдельными вызовами `collectAsStateWithLifecycle()`.

**Плюсы**
- Полностью снимает вопрос лимита `combine` для UI-состояния — каждый под-поток комбинируется независимо в своих пределах.
- Recomposition становится точнее: изменение тумблера настроек не пересобирает часть UI, зависящую только от списка задач.

**Минусы**
- Более заметный рефакторинг `TaskListScreen.kt` — несколько `state`-переменных вместо одной, придётся передавать несколько объектов в дочерние composable вместо одного `state`.
- Не решает проблему для `syncStatus` (:122), если он продолжит расти — там расщепление источников менее естественно (все поля обычно нужны вместе).

**Когда выбирать:** когда `TaskListUiState` вырастет насколько, что recomposition всего списка на каждый чих (например, каждую секунду от `syncManager.lastSyncAt`) станет заметной проблемой производительности, а не просто эстетическим неудобством.

## Вариант C — vararg `combine` для однотипных потоков

Использовать `combine(vararg flows: Flow<Boolean>) { array -> ... }` конкретно для группы взаимозаменяемых bool-тумблеров настроек (все `…Flow: Flow<Boolean>` из `PreferencesManager` имеют одинаковый тип).

**Плюсы**
- Не появляется новый data-класс на каждый добавленный тумблер — просто дописать поток в список.
- Хорошо подходит именно для роста числа **однотипных** флагов (bool-настроек), которых, вероятно, будет больше всего в будущем.

**Минусы**
- Теряется типобезопасность на границе — обращение по индексу массива (`array[0]`, `array[1]`) вместо именованных полей, что легко перепутать при рефакторинге.
- Не универсален — не подходит для разнотипных потоков (`syncStatus` этим методом не улучшить).

**Когда выбирать:** если в будущем появится действительно много (5+) независимых bool-тумблеров в духе экспериментальных фич — тогда компромисс (потеря типобезопасности ради отсутствия постоянного дописывания data-классов) может окупиться.

## Сводная таблица

| | Сложность внедрения | Типобезопасность | Решает `syncStatus` | Решает `uiState` | Когда актуально |
|---|---|---|---|---|---|
| **A — вкладывать дальше** | низкая | полная | да | да | сейчас, по умолчанию |
| **B — расщепить на несколько StateFlow** | средняя (рефакторинг экрана) | полная | нет | да | когда recomposition станет проблемой |
| **C — vararg для bool-тумблеров** | низкая | частичная (по индексу) | нет | да, для тумблеров | при взрывном росте числа bool-флагов |

## Рекомендация

Действовать нужно не сейчас, а **в момент следующего переполнения** — то есть когда появится очередной кандидат в `syncStatus` или `uiState`. Тогда:

- Если это ещё один bool-тумблер настроек (как `showPendingSyncIndicator`) — сгруппировать существующие и новые тумблеры в один `Toggles`-data-класс (вариант A, применённый конкретно к этой категории). Это устраняет корень проблемы: сейчас каждый новый тумблер отдельно ест слот `uiState`, хотя логически все тумблеры — одна тема.
- Если это состояние синхронизации, близкое к `syncStatus`, — завести внутри него ещё один уровень вложенности по той же схеме, что уже сделано для `syncTimestamps`.
- Вариант B — держать в уме как решение на случай, если экран начнёт заметно тормозить при частых обновлениях (`syncManager.lastSyncAt` тикает каждую секунду во время синка) — это на сегодня не наблюдалось и не является поводом делать рефакторинг превентивно.
- Вариант C не рекомендуется как первый шаг — вводить его стоит только если группировка через `Toggles`-класс (вариант A) сама начнёт распухать (5+ полей) настолько, что каждое добавление ощутимо разрастает конвейер.

## Оценка объёма

- **A (следующая группировка):** ~15–20 минут на переполнение — завести data-класс, обновить один `combine`, прокинуть поля.
- **B:** несколько часов — рефакторинг `TaskListScreen.kt` под несколько `collectAsStateWithLifecycle()`, ревизия всех мест, где composable принимают `state: TaskListUiState` целиком.
- **C:** ~30 минут на внедрение, но добавляет постоянный риск ошибок по индексу при каждой последующей правке.
