# Предложение: ежедневное уведомление-сводка «дел на сегодня»

## Контекст

Идея пользователя: в разделе настроек «Уведомления» добавить ещё один тумблер — «Ежедневная сводка». При включении под тумблером появляется строка «Напомнить в HH:mm» с выбором времени; при выключении строка исчезает, чтобы не вводить в заблуждение. По умолчанию (первое включение) — 08:00, при повторных включениях — последнее выставленное пользователем значение. Уведомление приходит в указанное время каждый день и показывает количество дел на сегодня — **даже если дел ноль** (явно «0», не молчание), чтобы отсутствие уведомления никогда не путалось с «дел нет».

Документ фиксирует: (1) какие вопросы по смыслу фичи нужно закрыть до реализации, (2) какие механизмы планирования ежедневного будильника рассматривались и почему, (3) какие технические компоненты потребуется добавить и куда они лягут по существующей архитектуре.

---

## Развилка 1 — что считать «делами на сегодня»

Готового запроса под это в `TaskDao` нет (см. `docs/database-access.md`) — есть только `observeActiveTasks()`/`observeAllTasks()`, фильтрация по `assignedTo`/`dueDate` сейчас делается вручную в `TaskListViewModel`. Для новой фичи нужно явно зафиксировать три независимых решения:

**1a. Чьи задачи считать.**
- **Вариант A (рекомендован)** — только `assignedTo == myDeviceId`, по аналогии с `AssigneeFilter.MINE`. Логика: уведомление отвечает на вопрос «что сегодня должен сделать я», а не «что вообще происходит в семье».
- Вариант B — все активные задачи независимо от назначения. Может быть избыточным шумом, если партнёр назначает задачи сам себе.

**1b. Просроченные задачи.**
- **Вариант A (рекомендован)** — строго `dueDate` попадает в сегодняшние сутки (полночь–полночь), просроченные (`dueDate` в прошлом, не done) в счётчик не входят — они уже показаны как «Просрочено» в основном списке (см. «Разделители по датам» в CLAUDE.md), дублировать не нужно.
- Вариант B — включать просроченные в счётчик «на сегодня», чтобы сводка была тревожнее. Стоит явно отклонить или принять — сейчас неопределённость.

**1c. `isSecret`-задачи.**
- Уведомление целиком локальное (не уходит по сети), поэтому запрет «`isSecret` никогда не покидает устройство» тут не нарушается технически. Вопрос чисто UX: должен ли секретный пункт учитываться в числе, которое может увидеть кто угодно, глянувший на экран блокировки (уведомление на lock screen читаемо посторонним)? **Рекомендация — исключать `isSecret` из счётчика**, тем же принципом, что и в списке задач/API веб-интерфейса: секретное не должно проявляться нигде, куда не требуется явно зайти в приложение.

Эти три пункта нужно подтвердить (или переопределить) явно — от них зависит запрос к `TaskRepository`, который будет выполнять воркер.

## Развилка 2 — механизм ежедневного будильника

Ключевое отличие от всех существующих уведомлений в проекте: due-уведомления и recurrence-spawn — это **одноразовые** `OneTimeWorkRequestBuilder` с `setInitialDelay` до конкретного будущего момента (`NotificationScheduler.scheduleDueNotifications`). Здесь нужен **wall-clock будильник, повторяющийся каждый день в фиксированное локальное время** — паттерна для этого в проекте пока нет; ближайший прецедент по требованиям (пережить Doze, сработать точно) — это `keepAlive` (`performKeepAlive()`, раз в час через `AlarmManager.setExactAndAllowWhileIdle`).

### Вариант A — `AlarmManager.setExactAndAllowWhileIdle` + самопланирование (рекомендован)

Будильник ставится на следующее наступление HH:mm (сегодня, если ещё не наступило, иначе завтра), считает задачи, показывает уведомление и в конце **сам** ставит следующий будильник на +24 часа расчётным способом (не `+24*60*60*1000` слепо — через `Calendar`, чтобы корректно пережить переход на летнее/зимнее время). Точно то же самое семейство API, что уже используется в `performKeepAlive`.

Плюсы: точное время срабатывания, будит устройство в Doze, не требует новых разрешений (`USE_EXACT_ALARM`/`SCHEDULE_EXACT_ALARM` уже в манифесте), полностью следует уже проверенному в проекте паттерну.

Минусы: требует ручного самопланирования (реализовать «поставить будильник на следующий день» самостоятельно) и восстановления после ребута — `BootReceiver.kt` сейчас **не** переустанавливает вообще ничего, кроме запуска `SyncService` (WorkManager сам переживает перезагрузку, а голый `AlarmManager` — нет), значит сюда придётся добавить логику пересчёта следующего срабатывания при `ACTION_BOOT_COMPLETED`. Также нужно самостоятельно слушать `ACTION_TIME_CHANGED`/`ACTION_TIMEZONE_CHANGED`, иначе смена времени на устройстве или часового пояса (актуально не для этого приложения — оно только про одну семью в одной сети, но всё равно возможно, например, в поездке) может сдвинуть будильник.

### Вариант B — `AlarmManager.setAlarmClock()`

Формально самый надёжный API в Android: полностью освобождён от Doze/battery-ограничений, гарантированно точное время. Побочный эффект — постоянная иконка будильника в статус-баре устройства, пока будильник запланирован (то есть всегда, раз он ежедневный). Такая иконка уместна для настоящих будильников/таймеров, но для фичи «сводка задач» будет визуально сбивать с толку пользователя (создаёт впечатление, что где-то стоит настоящий будильник).

**Отклонён** по этой причине — цена (постоянная иконка) не оправдана выигрышем в надёжности, который и так достаточен в варианте A для срабатывания раз в сутки.

### Вариант C — `WorkManager.PeriodicWorkRequest` (интервал 24 часа)

Самый простой в реализации — WorkManager сам переживает перезагрузку без правок `BootReceiver`, не требует ручного самопланирования.

Минус — не гарантирует точное время суток: минимальный интервал негибок, есть накопительный дрейф, и на агрессивных OEM (Samsung One UI — уже задокументированная в `docs/background-reachability.md` проблема этого же проекта) периодическая задача откладывается системой до ближайшего «окна обслуживания», иногда на часы. Для фичи, где пользователь явно указывает «напомнить **в** 08:00», такой разброс противоречит сути функции.

**Отклонён** для основного варианта, но может быть fallback-подсказкой в документации («если точность неважна — проще»reserved, не реализуется).

### Итог развилки

| Вариант | Точность времени | Переживает Doze | Требует правки BootReceiver | Побочные эффекты UI | Решение |
|---|---|---|---|---|---|
| A — `setExactAndAllowWhileIdle` + self-reschedule | высокая | да | да (новая логика) | нет | **выбран** |
| B — `setAlarmClock()` | высокая | да (по конструкции) | да | постоянная иконка будильника в статус-баре | отклонён |
| C — `PeriodicWorkRequest` 24ч | низкая, дрейфует | не гарантированно (Doze maintenance windows, особенно One UI) | нет | нет | отклонён |

## Что потребуется добавить (по компонентам)

- **`PreferencesManager.kt`** — новые ключи: `dailySummaryEnabled: Boolean` (default `false`), `dailySummaryHour: Int`, `dailySummaryMinute: Int` (default 8/0). По паттерну существующих `notifyDueDate`/`notifyNewTask`/`notifyStatusChange`.
- **Новый notification channel** `ch_daily_summary` в `NotificationScheduler.createChannels()` — по конвенции проекта каждый смысловой тип уведомления получает отдельный канал (сводка — не то же самое, что due-date/new-task/status).
- **Планировщик** — новая функция в `NotificationScheduler` (например `scheduleDailySummaryAlarm()` / `cancelDailySummaryAlarm()`), использующая `AlarmManager` напрямую (не через `WorkManager`, как due-уведомления) — по образцу того, как `keepAlive` уже устроен в `SyncService`.
- **`BroadcastReceiver`** (новый, например `DailySummaryReceiver`, аналог по роли `KeepAliveReceiver`) — получает будильник, считает задачи через `TaskRepository` (по определениям из развилки 1), показывает уведомление, сам себя переставляет на следующий день.
- **`BootReceiver.kt`** — добавить переустановку будильника при `ACTION_BOOT_COMPLETED`, если `dailySummaryEnabled == true` (сейчас там нет ничего, кроме запуска `SyncService`).
- **`SettingsScreen.kt` / `SettingsViewModel`** — новый `SwitchRow` в секции «Уведомления» + условная строка времени, открывающая `TimePickerDialog` (переиспользовать паттерн из `CreateTaskScreen.pickDateTime()`, но без `DatePickerDialog` — нужен только час/минута, без даты). При изменении тумблера/времени — пересоздать будильник (`cancelDailySummaryAlarm()` + `scheduleDailySummaryAlarm()`).

Всё перечисленное — целиком локальная фича: не затрагивает `MergeTasksUseCase`, `SyncDto`, схему БД или sync-протокол.

## Не планируется (пока)

- Настройка содержимого текста уведомления (например «У тебя 3 дела» vs «3 задачи ждут») — фиксированный шаблон в v1.
- Несколько напоминаний в день — только одно ежедневное время, как и запрошено.
- Учёт часового пояса партнёра — будильник целиком локальный, у каждого устройства свои настройки времени независимо друг от друга (как и весь остальной UI/уведомления в проекте).

## Рекомендация

Сначала явно закрыть развилку 1 (что считать «делами на сегодня» — рекомендованы варианты A/A/A: только мои задачи, без просроченных, без `isSecret`), затем реализовывать по варианту A развилки 2 (`AlarmManager.setExactAndAllowWhileIdle` + самопланирование), как прямое расширение уже проверенного в проекте паттерна `keepAlive`. Объём работы сопоставим с этой уже существующей фичей.
