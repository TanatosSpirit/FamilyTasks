# Предложения: улучшения чек-листа поверх текущей реализации

## Контекст

Базовая версия чек-листа реализована по `proposal/checklist-in-task-description.md` и плану `delegated-hopping-balloon`: `ChecklistItem` как сериализованное поле `Task.checklist`, редактор строк в форме создания/редактирования, мгновенный тоггл на экране деталей, сброс галочек при клонировании повторяющихся задач. Часть идей из исходного разбора сознательно осталась за скобками первой итерации — этот документ их собирает, чтобы решить, что и когда делать дальше.

Все пункты независимы друг от друга — можно брать по одному, в любом порядке.

---

## 1. Прогресс «N из M» в карточке списка задач

Сейчас `TaskListScreen.kt` показывает только иконку `Description`, если у задачи есть описание; про наличие и состояние чек-листа в списке ничего не видно — надо открыть задачу.

**Что предлагается:** для задач с непустым `checklist` показывать в карточке текст вида «3 из 7» (или узкий прогресс-бар) — сколько пунктов отмечено из общего числа.

**Плюсы**
- Главная ценность списка задач — окинуть взглядом состояние всех дел не открывая их; чек-лист без этого «непрозрачен» в списке.
- Дёшево вычисляется: `checklist.count { it.checked }` / `checklist.size`, готовый JSON уже распарсен в `Task.checklist` на слое `toDomain()`, лишнего запроса к БД не требует.

**Минусы**
- Карточка и так насыщена (приоритет, дедлайн, исполнитель, pending-sync индикатор) — нужно аккуратно найти место, не перегружая.
- Для задач с длинным списком пунктов сам факт «3 из 7» может быть менее информативен, чем открыть и посмотреть, какие именно остались — это дополнение к просмотру, не замена.

**Оценка:** маленькая правка, один файл (`TaskListScreen.kt`), без изменений модели. ~30 минут.

**Рекомендация:** делать одним из первых — самая дешёвая и заметная польза.

## 2. Drag-to-reorder пунктов

Сейчас порядок пунктов — порядок ввода; поменять местами можно только удалив и создав заново.

**Что предлагается:** в `ChecklistEditor` — перетаскивание строк (например через `Modifier.pointerInput` + `LazyColumn` с `reorderable`-паттерном, либо сторонняя библиотека при желании).

**Плюсы**
- Реальный сценарий: собрали список, поняли что порядок неудобен (сначала документы, потом одежда) — сейчас единственный способ пересобрать это — стереть и напечатать заново.

**Минусы**
- Самый дорогой пункт в списке: drag-and-drop в Compose не тривиален (`detectDragGesturesAfterLongPress`, пересчёт индексов на лету, автоскролл при перетаскивании к краю экрана при длинных списках).
- `ChecklistEditor` сейчас — простой `Column` с построчным рендером внутри формы, которая сама скроллится (`verticalScroll` на весь экран в `CreateTaskScreen`/`EditTaskContent`); drag внутри вложенного скролла обычно требует более явного управления скроллом (`LazyColumn` не комбинируется с внешним `verticalScroll` без переделки структуры экрана).
- Пользы для типичных списков (чемодан, покупки — обычно 5-15 пунктов) может не окупать сложность: до/после через удаление+пересоздание для такого объёма не так болезненно.

**Оценка:** день+ с учётом переделки скролл-структуры формы под `LazyColumn`.

**Рекомендация:** отложить до явного запроса от использования — не самая частая потребность для списков такого масштаба.

## 3. Шаблоны чек-листов («Чемодан», «Покупки»)

Из исходного `proposal/checklist-in-task-description.md` (Вариант 3) — кнопка «Вставить шаблон» в `ChecklistEditor`, разворачивающая заготовленный список пунктов одним тапом.

**Плюсы**
- Закрывает самый частый кейс («собрать чемодан») без набора текста вообще — экономит время именно в том сценарии, который и был поводом для фичи.
- Не требует нового формата хранения — шаблон это просто список строк, разворачивающийся в обычные `ChecklistItem` через уже существующий `onItemsChange`.

**Минусы**
- Нужен диалог выбора шаблона + сами шаблоны где-то хранить: как захардкоженные константы (просто, но негибко — нельзя завести свой шаблон) или как редактируемую пользователем сущность (уже требует своего маленького UI и, возможно, места в БД).
- Хардкод универсальных шаблонов рискует не подойти конкретной семье (набор для «чемодана» у всех разный) — есть шанс, что фича будет использоваться один раз ради любопытства и забудется.

**Оценка:** с захардкоженными константами — небольшая, ~1-2 часа (диалог выбора + список из 2-3 шаблонов). С пользовательскими шаблонами — сравнимо с целой новой фичей, не рекомендуется сразу.

**Рекомендация:** делать только версию с захардкоженными константами, если вообще делать; пользовательские шаблоны — не сейчас.

## 4. Продолжение ввода по Enter (как в Google Keep/Reminders)

Сейчас в `ChecklistEditor` для добавления пункта нужно каждый раз тапать «+ Добавить пункт» — при вводе длинного списка это происходит после каждой строки. Изначально обсуждавшийся образец (Google Keep/Reminders) подразумевал, что Enter/Done на клавиатуре в поле текущего пункта сразу создаёт следующую пустую строку и переводит фокус на неё — эта часть была сознательно упрощена в первой итерации ради меньшего риска.

**Плюсы**
- Меньше тапов при вводе списка из нескольких пунктов подряд — то самое «печатать не отрываясь», ради чего вариант 1 предпочли markdown ещё на этапе выбора подхода.

**Минусы**
- Требует управления фокусом (`FocusRequester` на каждую строку + `LaunchedEffect`, реагирующий на добавление нового пункта) — немного состояния, которого сейчас в `ChecklistEditor` нет вообще (он полностью stateless).
- Нужно аккуратно обработать край: Enter на *пустой* последней строке не должен плодить пустые пункты бесконечно (закрывать ввод вместо этого).

**Оценка:** небольшая, но требует внимательности — половина дня с ручной проверкой поведения клавиатуры на устройстве.

**Рекомендация:** второй кандидат после прогресса в списке (#1) — ощутимо улучшает именно тот сценарий, ради которого затевалась фича, и не требует изменений модели данных.
