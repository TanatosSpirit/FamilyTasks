# Proposal: Подавление эхо-sync после входящей синхронизации

**Статус:** предлагается к реализации  
**Приоритет:** низкий  
**Затрагивает:** `SyncService.kt`

---

## Проблема

`observeTaskChanges` реагирует на **любую** запись в БД через Room — в том числе на записи, сделанные `mergeAll` внутри `onSyncRequest` (входящий sync от партнёра). Различить «пользователь изменил задачу» и «задача пришла по сети» он не может.

Следствие: через 3 секунды после получения входящего sync (debounce) устройство само инициирует `triggerSync()` и отправляет ту же задачу обратно партнёру. Партнёр видит `=1 unchanged` и ничего не пишет в БД — эхо обрывается.

---

## Сценарий (воспроизведён в логах от 2026-06-28)

```
18:56:16  [B] triggerSync → A: Delta sending 1/44 (изменение от пользователя)
18:56:16  [A] onSyncRequest: mergeAll → task updated, пишет в БД
18:56:16  [A] Responded with 1 tasks
          ↓ observeTaskChanges на A видит запись → debounce 3s
18:56:19  [A] triggerSync → B: Delta sending 1/44  ← лишний раунд
18:56:19  [B] Merge done: =1 unchanged             ← ничего не изменилось
```

До delta sync эхо отправляло 44 задачи. С delta sync — 1. Стало дешевле, но не исчезло.

---

## Почему это стоит исправить

- **Шум в логах.** Лишние строки `triggerSync`, `Delta: sending`, `Sync OK` затрудняют чтение, особенно при частых изменениях.
- **Лишний HTTP round-trip.** Малозаметно при хорошем сигнале, но каждый `POST /sync` — это CPU (сериализация), WiFi activity и удержание WakeLock на время запроса.
- **Паразитный debounce.** После применения входящего sync А ждёт 3 секунды перед отправкой. Если за эти 3 секунды пользователь что-то изменит — debounce сбросится и уйдёт нормальный sync. Если нет — уйдёт бессмысленный эхо. Ситуация немного запутывает и чтение логов, и анализ трафика.

---

## Предлагаемое решение

Запоминать время последнего завершённого входящего merge. Если `observeTaskChanges` срабатывает в окне `debounce + буфер` после этого события — подавлять `triggerSync()`.

### Реализация

В `SyncService`:

```kotlin
@Volatile private var lastIncomingSyncAt = 0L

// В onSyncRequest, после mergeAll:
lastIncomingSyncAt = System.currentTimeMillis()

// В observeTaskChanges:
.debounce(3_000L)
.collect {
    val msSince = System.currentTimeMillis() - lastIncomingSyncAt
    if (msSince < 4_000L) {   // debounce (3s) + буфер (1s)
        AppLogger.d(TAG, "observeTaskChanges: echo suppressed (incoming ${msSince}ms ago)")
        return@collect
    }
    triggerSync()
}
```

`lastIncomingSyncAt` — `@Volatile`, не персистируется. При рестарте сервиса = 0, первая эмиссия всегда пройдёт.

---

## Edge case: пользователь меняет задачу вскоре после входящего sync

Если пользователь изменяет задачу **менее чем через 1 секунду** после входящего sync:
- `observeTaskChanges` сбрасывает debounce
- Debounce завершается через 3 секунды после изменения пользователя
- `msSince` к этому моменту ≈ 4 сек — граничная зона

В таком случае возможна ложная супрессия — изменение пользователя не уйдёт немедленно. Оно уйдёт позже при:
- следующем изменении любой задачи
- keepAlive (до 1 часа)
- WiFi reconnect

Для семейного приложения с debounce 3 сек этот сценарий редкий и последствия незначительные.

---

## Более надёжная альтернатива

Явно отслеживать **момент последнего пользовательского изменения** (`lastUserInitiatedChangeAt`), обновляемый из ViewModel при каждом сохранении задачи. Тогда в `observeTaskChanges`:

```kotlin
if (lastIncomingSyncAt > lastUserInitiatedChangeAt) {
    // последнее что писало в БД — входящий sync, а не пользователь → подавить
    return@collect
}
triggerSync()
```

**Плюсы:** нет граничной зоны, логика точная.  
**Минусы:** ViewModels должны уведомлять SyncService о пользовательских изменениях — новая связь между слоями. Сейчас ViewModels работают через Repository и ничего не знают о SyncService.

**Рекомендация:** начать с timestamp-окном (проще, изолировано в `SyncService.kt`). Переходить к явному отслеживанию только если edge case с 1-секундным окном подтвердится на практике в логах.

---

## Что не меняется

- Логика `observeTaskChanges` (порядок операторов, debounce) — не трогается.
- Поведение при пользовательских изменениях — без изменений.
- Протокол sync — без изменений.
- Если оба устройства изменяют задачу одновременно — `syncMutex` защищает как раньше.
