## 1. Обзор архитектуры

Syncthing — децентрализованная P2P-система синхронизации файлов. Не требует центрального сервера для хранения данных. Устройства (nodes) образуют кластер и обмениваются файлами напрямую.

### Стек протоколов

```
┌─────────────────────────────────────┐
│      Block Exchange Protocol (BEP)  │  ← логика синхронизации файлов
├─────────────────────────────────────┤
│      Encryption & Auth (TLS 1.3)    │  ← шифрование и аутентификация
├─────────────────────────────────────┤
│      Reliable Transport (TCP/QUIC)  │  ← надёжная доставка пакетов
├─────────────────────────────────────┤
│      Discovery (UDP / HTTPS)        │  ← нахождение устройств в сети
└─────────────────────────────────────┘
```

### Ключевые принципы

- **Pull-модель передачи данных** — блоки запрашивает тот, кому их не хватает; никакого "толкания" лишних данных
- **Content-addressing** — файлы идентифицируются по SHA-256 хэшам блоков, а не по именам
- **Delta-синхронизация** — передаются только изменившиеся блоки внутри файла
- **Конец-в-конец шифрование** — данные шифруются до передачи, relay-серверы не могут их читать

## 2. Слой 1 — Обнаружение устройств (Discovery)

Прежде чем начать синхронизацию, устройства должны найти друг друга. Syncthing использует трёхуровневую систему обнаружения.

### 2.1 Local Discovery (LAN)

| Параметр | Значение |
|---|---|
| Протокол | UDP |
| Порт | 21027 |
| IPv4 | broadcast на `255.255.255.255` |
| IPv6 | multicast на `ff12::8384` |
| Интервал | каждые 30 секунд |

Устройства, находящиеся в одной локальной сети, отвечают на broadcast своим адресом прослушивания. При наличии LAN-связи глобальный discovery не нужен — устройства соединяются напрямую.

### 2.2 Global Discovery

| Параметр | Значение |
|---|---|
| Протокол | HTTPS |
| Назначение | поиск устройств за пределами LAN |
| Интервал анонсирования | каждые 30 минут |
| Содержимое анонса | Device ID + порт прослушивания |

Устройство регистрируется на публичных discovery-серверах. При поиске партнёра отправляется запрос с его Device ID — сервер возвращает последний известный IP:port.

Соединение с discovery-сервером защищено TLS с верификацией сертификата сервера.

### 2.3 Relay Servers

Используются как fallback, если прямое соединение невозможно (симметричный NAT, строгий файрволл).

Relay работает по аналогии с TURN-протоколом: пересылает зашифрованный трафик между устройствами. Relay не может расшифровать данные — TLS-сессия установлена напрямую между конечными устройствами.

Relay по умолчанию включён. Можно отключить или указать конкретные доверенные relay-серверы.

### 2.4 Дополнительные методы подключения

- **Статические адреса** — явное указание IP:port партнёра в конфигурации
- **NAT Traversal (hole punching)** — попытка установить прямое соединение через NAT без relay
- **История устройств** — кэш ранее успешных адресов

## 3. Слой 2 — Транспорт и аутентификация (TLS 1.3)

### 3.1 Идентификация устройств (Device ID)

Каждое устройство при первом запуске генерирует самоподписанный X.509 сертификат. Device ID — это SHA-256 хэш сертификата, представленный в человекочитаемой кодировке.

```
Device ID пример:
MFZWI3D-BONSGYC-X4QLOGI-Y5MXUA7-IJNKPLB-STEK3QQ-A7EWLM5-IYXANAQ
```

Device ID одновременно является:

- уникальным идентификатором устройства
- криптографическим доказательством владения ключом
- основой для аутентификации (certificate pinning)

### 3.2 Установка соединения

```
Устройство A                         Устройство B
     │                                    │
     │──── TLS ClientHello ──────────────►│
     │◄─── TLS ServerHello + Certificate ─│
     │──── Certificate (A) ──────────────►│
     │                                    │
     │  [Обе стороны проверяют SHA-256   ]│
     │  [отпечаток сертификата партнёра  ]│
     │  [по заранее известному Device ID ]│
     │                                    │
     │══════ Encrypted Channel ═══════════│
     │                                    │
     │──── Hello message ────────────────►│  ← device_name, client_version
     │◄─── Hello message ─────────────────│
     │                                    │
     │  [Если Device ID не в белом списке]│
     │  [— соединение разрывается]        │
```

Аутентификация взаимная (mutual TLS). Оба устройства обязаны иметь сертификат друг друга в списке доверенных.

### 3.3 Параметры TLS

| Параметр | Значение |
|---|---|
| Минимальная версия | TLS 1.3 |
| Аутентификация | Certificate pinning (SHA-256) |
| Порт синхронизации | 22000 (TCP по умолчанию) |
| Хэш сертификата | SHA-256 |

## 4. Слой 3 — Block Exchange Protocol (BEP)

BEP — прикладной протокол Syncthing, работающий поверх TLS-соединения. Определяет формат сообщений для обмена индексами файлов и данными блоков.

### 4.1 Формат сообщения

Каждое сообщение состоит из трёх частей:

```
┌──────────────────────┐
│  Header Length (16b) │  ← длина заголовка
├──────────────────────┤
│       Header         │  ← тип сообщения, сжатие (protobuf)
├──────────────────────┤
│  Message Length (32b)│  ← длина тела
├──────────────────────┤
│       Message        │  ← тело (protobuf, опционально LZ4)
└──────────────────────┘
```

Все числа в network byte order (big endian).

### 4.2 Типы сообщений

| Тип | Направление | Описание |
|---|---|---|
| `CLUSTER_CONFIG` | оба → | Первое сообщение после auth. Список синхронизируемых папок и устройств |
| `INDEX` | оба → | Полный индекс папки: все файлы с хэшами блоков |
| `INDEX_UPDATE` | оба → | Только изменения индекса с последней синхронизации (delta) |
| `REQUEST` | инициатор → | Запрос конкретного блока файла (имя файла, offset, size, hash) |
| `RESPONSE` | партнёр → | Ответ с данными блока |
| `DOWNLOAD_PROGRESS` | оба → | Уведомление о прогрессе загрузки (для multi-source) |
| `PING` | оба → | Keepalive для поддержания соединения |
| `CLOSE` | оба → | Корректное закрытие соединения |

### 4.3 Сжатие

| Режим | Значение | Применение |
|---|---|---|
| `NONE` | 0 | Без сжатия |
| `LZ4` | 1 | Метаданные (Index, Index Update) всегда; Response — опционально |

Сжатие LZ4 применяется к protobuf-сообщению целиком. Перед сжатым блоком передаётся 32-битное поле с размером несжатых данных.

### 4.4 Protobuf-схема ключевых сообщений

**ClusterConfig** (первое сообщение сессии):
```protobuf
message ClusterConfig {
    repeated Folder folders = 1;
}

message Folder {
    string id     = 1;   // уникальный ID папки
    string label  = 2;   // человекочитаемое имя
    FolderType type = 3;
    repeated Device devices = 16;
}

enum FolderType {
    SEND_RECEIVE      = 0;
    SEND_ONLY         = 1;
    RECEIVE_ONLY      = 2;
    RECEIVE_ENCRYPTED = 3;
}
```

**REQUEST** (запрос блока):
```protobuf
message Request {
    int32  id          = 1;   // ID запроса (для матчинга с Response)
    string folder      = 2;   // ID папки
    string name        = 3;   // путь к файлу
    int64  offset      = 4;   // смещение блока в файле
    int32  size        = 5;   // размер блока
    bytes  hash        = 6;   // ожидаемый SHA-256 хэш блока
    bool   from_temporary = 7;
}
```

## 5. Слой 4 — Блочная модель файлов

### 5.1 Разбивка файла на блоки

Каждый файл делится на блоки одинакового размера. Размер блока зависит от размера файла и выбирается из ряда степеней двойки:

| Размер файла | Размер блока |
|---|---|
| до ~256 КиБ | 128 КиБ |
| до ~512 КиБ | 256 КиБ |
| до ~1 МиБ | 512 КиБ |
| ... | ... |
| свыше ~384 МиБ | 16 МиБ (максимум) |

Последний блок файла может быть меньше стандартного размера.

### 5.2 Block List

Для каждого файла вычисляется **block list** — список записей вида:

```
{ offset: int64, size: int32, hash: bytes(32) }
```

Именно block list хранится в индексе и передаётся между устройствами. Сами данные файла передаются только по запросу.

### 5.3 Алгоритм синхронизации файла

```
1. Получить block list желаемой версии от партнёра
2. Сравнить с block list локальной версии
3. Для каждого отличающегося блока:
   a. Проверить: есть ли блок с таким же hash локально
      (в другом файле или другом месте того же файла)?
      → Если да: скопировать с диска (без сетевого трафика)
   b. Если нет: отправить REQUEST партнёру
4. Получить RESPONSE с данными блока
5. Вычислить SHA-256 полученного блока
6. Если hash совпадает с ожидаемым — записать во временный файл
7. Если не совпадает — отбросить, запросить снова
8. После сборки всех блоков: атомарно переместить временный
   файл на место целевого (rename)
```

Файл никогда не записывается напрямую — всегда через временный файл вида `.syncthing.<name>.tmp`. Это обеспечивает атомарность операции.

### 5.4 Multi-source синхронизация

Если в кластере несколько устройств имеют нужный файл, блоки могут запрашиваться **параллельно с разных устройств** — аналогично BitTorrent. Это ускоряет синхронизацию при большом количестве устройств.

## 6. Слой 5 — Delta Index Exchange

Механизм, позволяющий избежать полной передачи индекса при каждом переподключении.

### 6.1 Принцип работы

Каждый файл в индексе имеет монотонно возрастающий `sequence_number`. При первом соединении устройства:
- обмениваются полными `INDEX`-сообщениями
- сохраняют `index_id` (уникальный идентификатор набора индексных данных) и `max_sequence` партнёра

При последующих соединениях:
- устройство передаёт в `ClusterConfig` свой `index_id` и `max_sequence`
- партнёр видит, что этот `index_id` ему известен, и отправляет только `INDEX_UPDATE` с записями, имеющими `sequence_number > max_sequence`

### 6.2 Выгода для мобильных устройств

Допустим, синхронизируется папка с 100 000 файлов. При переподключении телефона после ночи, когда изменилось 5 файлов:

| Подход | Объём передаваемых метаданных |
|---|---|
| Полный INDEX | пропорционален 100 000 записям |
| Delta (INDEX_UPDATE) | 5 записей |

Снижение сетевой активности при переподключении — на порядки.

## 7. Обнаружение изменений на устройстве

### 7.1 Filesystem Watcher

Основной метод обнаружения изменений. Подписка на события файловой системы через OS API (inotify на Linux, аналоги на Android/Windows/macOS).

Параметры обработки событий:

| Событие | Задержка перед сканированием |
|---|---|
| Изменение / создание файла | 10 секунд (накопление изменений) |
| Удаление файла | 1 минута |

Задержка нужна для батчинга: если приложение сохраняет файл многократно за несколько секунд (автосохранение), запускается только одно сканирование.

### 7.2 Периодическое полное сканирование

Резервный механизм на случай пропущенных событий watcher.

| Параметр | Значение |
|---|---|
| Интервал по умолчанию | 1 час |
| Разброс | от 0.75× до 1.25× интервала (предотвращает синхронный rescan всех папок) |

### 7.3 Процедура сканирования

При сканировании (полном или от watcher) для каждого файла проверяются:
- время модификации (mtime)
- размер
- биты прав доступа

Если хотя бы один параметр изменился — пересчитывается block list (rehash файла). Без изменения атрибутов файл повторно не хэшируется — это экономит CPU.

## 8. Управление конфликтами

### 8.1 Обнаружение конфликта

Конфликт возникает, когда файл изменён на двух устройствах одновременно (до того, как изменения успели синхронизироваться).

### 8.2 Разрешение конфликта

Syncthing не пытается объединить содержимое (нет merge). Вместо этого:

1. Файл с более старым временем модификации переименовывается:
   `<name>.sync-conflict-<YYYYMMDD>-<HHMMSS>-<deviceID>.<ext>`
2. Победитель (более новый mtime) остаётся под оригинальным именем
3. Если mtime одинаков — победитель определяется по первым 63 битам Device ID (детерминированно, но произвольно)
4. При конфликте изменения vs. удаления — файл переименовывается в conflict-копию

Conflict-файлы синхронизируются между всеми устройствами кластера как обычные файлы.

## 9. Особенности Android

### 9.1 Run Conditions

Android-версия Syncthing поддерживает гибкое управление условиями запуска:

| Условие | Описание |
|---|---|
| Только при зарядке | не работает от батареи |
| Только по Wi-Fi | не использует мобильный интернет |
| Временны́е окна | например, 5 минут каждый час |
| Только при наличии партнёра | не держит соединение впустую |

### 9.2 Источники энергопотребления и оптимизации

| Источник расхода | Механизм оптимизации |
|---|---|
| Wi-Fi радиомодуль | Delta-синхронизация: передаётся минимум данных за сессию |
| CPU в фоне | Filesystem watcher вместо polling |
| CPU при переподключении | Delta Index Exchange: нет полной пересылки индекса |
| Постоянное соединение | Настраиваемые Run Conditions |
| Discovery-трафик | Local discovery раз в 30 сек, global — раз в 30 мин |

### 9.3 Управление фоновой работой

Android агрессивно завершает фоновые процессы (Doze Mode, App Standby). Syncthing использует Foreground Service с уведомлением, чтобы сохранять процесс живым во время активной синхронизации.

## 10. Сводная схема сессии

```
Телефон (A)                              Компьютер (B)
     │                                         │
     │   [Discovery]                           │
     │─── UDP broadcast ──────────────────────►│
     │◄── UDP response (addr:port) ────────────│
     │                                         │
     │   [TLS Handshake]                       │
     │─── ClientHello ────────────────────────►│
     │◄── ServerHello + Cert(B) ───────────────│
     │─── Cert(A) ────────────────────────────►│
     │   [Mutual certificate verification]     │
     │════════ Encrypted TLS 1.3 Channel ══════│
     │                                         │
     │   [BEP: Pre-auth]                       │
     │─── Hello {device_name, version} ───────►│
     │◄── Hello {device_name, version} ────────│
     │                                         │
     │   [BEP: Session init]                   │
     │─── ClusterConfig {folders} ────────────►│
     │◄── ClusterConfig {folders} ─────────────│
     │                                         │
     │   [BEP: Index exchange (delta)]         │
     │─── INDEX_UPDATE {seq > last_known} ────►│
     │◄── INDEX_UPDATE {seq > last_known} ─────│
     │                                         │
     │   [A обнаружил нехватку блоков]         │
     │─── REQUEST {file, offset, size, hash} ─►│
     │◄── RESPONSE {data (LZ4)} ───────────────│
     │─── REQUEST ... ────────────────────────►│
     │◄── RESPONSE ... ────────────────────────│
     │                                         │
     │   [Файл собран, проверен, перемещён]    │
     │─── INDEX_UPDATE {new seq} ─────────────►│
     │                                         │
     │   [Idle state]                          │
     │◄── PING ────────────────────────────────│
     │─── PING ───────────────────────────────►│
     │                                         │
     │   [Run Condition не выполнено]          │
     │─── CLOSE ──────────────────────────────►│
     │                                         │
```
