# Выбор при завершении повторяющейся задачи

При закрытии активной повторяющейся задачи, назначенной на себя, пользователю предлагается выбор: закрыть только текущее вхождение цепочки (и сразу создать следующее по правилу повтора) или закрыть всю цепочку (обычное завершение, повтор не продолжается).

До этой фичи любое завершение повторяющейся задачи — кнопкой в деталях или свайпом в списке — молча отменяло `RecurrenceSpawnWorker` (`cancelRecurrenceSpawn`), и следующее вхождение никогда не появлялось, даже если пользователь просто выполнил задачу раньше срока и не собирался прерывать повтор.

---

## Когда появляется диалог

Диалог показывается, только если у задачи есть что продолжать:

```
task.recurrence != Recurrence.None && task.dueDate != null && task.assignedTo == myDeviceId
```

Условие `assignedTo == myDeviceId` — по owner-only инварианту спавна (`docs/recurring-tasks.md`): клон порождает только устройство ответственного, поэтому предлагать «продолжить цепочку» имеет смысл только там, где у пользователя есть право что-то заспавнить. Если условие не выполняется (обычная задача без повтора, либо повторяющаяся, но назначенная партнёру) — завершение происходит как раньше, без диалога.

Проверяется в двух местах отдельно: `TaskDetailViewModel.isRecurringEligible()` и `TaskListViewModel.isRecurringEligible()` (идентичная приватная функция в обоих ViewModel).

---

## Два варианта

| Кнопка | Что происходит |
|---|---|
| **Завершить текущую** | Задача → `DONE`, `recurrence = None` (гашение, тот же маркер идемпотентности, что использует `RecurrenceSpawnWorker`). Сразу создаётся клон: `dueDate = recurrence.nextDueDate(исходный dueDate)`, `status = TODO`, новый `id`. Клону планируются due-уведомления и его собственный `RecurrenceSpawnWorker`. |
| **Завершить цепочку** | Прежнее поведение: задача → `DONE`, `recurrence` не трогается, `RecurrenceSpawnWorker` отменяется. Если потом вернуть задачу в `TODO` («Вернуть в работу»), `applyDueNotificationState` перепланирует спавн заново — цепочка воскресает. Это осознанно оставлено как есть. |

`nextDueDate` считается от **исходного `dueDate` задачи**, а не от момента нажатия кнопки — так же, как это делает `RecurrenceSpawnWorker` при обычном автоматическом спавне по дедлайну. Ранее завершение (до срока) не сдвигает график на текущий момент.

В отличие от автоматического спавна воркером, `notifyNewTask(clone)` **не вызывается** — пользователь сам инициировал продолжение и уже смотрит в приложение, уведомление о «новой задаче» было бы избыточным.

## Реализация

### `domain/usecase/RecurringTaskCompletionUseCase.kt`

Два метода, оба вызываются из обоих ViewModel:

- `completeEndingChain(task)` — обычное завершение (см. таблицу выше).
- `completeAndContinue(task)` — завершение + немедленный спавн следующего вхождения. Если `recurrence.nextDueDate()` вернуло `null` (защитный случай — правило не дало следующей даты), клон не создаётся, метод ведёт себя как `completeEndingChain`.

### Экран деталей (`TaskDetailViewModel.kt` / `TaskDetailScreen.kt`)

Кнопка «Готово» вызывает `onCompleteButtonClicked()`:
- Если задача `TODO` и eligible — выставляет `showRecurrenceChoice = true`, открывается `AlertDialog`.
- Иначе — обычный `cycleStatus()` (в т.ч. путь «Вернуть в работу», `DONE → TODO`, не меняется).

`confirmCompleteChain()` / `confirmCompleteAndContinue()` вызывают соответствующий метод use case и закрывают диалог.

### Список задач (`TaskListViewModel.kt` / `TaskListScreen.kt`) — свайп

Свайп для завершения (`docs/swipe-to-complete.md`) не может мгновенно закрыть задачу, если решение ещё не принято — иначе карточка визуально исчезнет раньше, чем появится диалог. Поэтому для eligible-задач жест **не завершает свайп** — карточка возвращается на место, а решение принимается через диалог:

```kotlin
// SwipeableTaskCard, confirmValueChange
if (fraction >= 0.3f) {
    onComplete()          // eligible → откроет диалог (см. ниже); иначе → сразу завершит
    !isRecurringEligible  // true = разрешить анимации дойти до конца; false = карточка возвращается
} else false
```

`onComplete()` — это по-прежнему `vm.completeTask(item.task)`. Сам `completeTask` решает:
- eligible → кладёт задачу в `_pendingRecurrenceTask` (не пишет в БД);
- иначе → сразу вызывает `recurringCompletion.completeEndingChain(task)`, как и раньше.

`TaskListScreen` подписан на `vm.pendingRecurrenceTask: StateFlow<Task?>` и показывает тот же `AlertDialog` на уровне экрана, если значение не `null`. `onDismissRequest` в обоих диалогах (список и детали) — просто закрыть диалог, ничего не менять: задача остаётся `TODO`, карточка в списке — на месте (потому что до подтверждения в БД ничего не записывалось).

---

## Что не меняется

- `RecurrenceSpawnWorker` — без изменений, обслуживает только автоматический (фоновый) спавн по дедлайну.
- `MergeTasksUseCase` — без изменений. Клон, созданный вручную через `completeAndContinue`, доезжает до партнёра обычным `/sync` и обрабатывается как обычная новая задача (та же ветка `local == null → added`, что и для клонов от `RecurrenceSpawnWorker`).
- `EditTaskContent` (переключение статуса через форму редактирования) диалогом не покрыт — путь используется существенно реже, чем кнопка в деталях и свайп.
