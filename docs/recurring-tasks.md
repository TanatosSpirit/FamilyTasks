# Повторяющиеся задачи

Задача с дедлайном и правилом повтора работает как «календарь напоминаний»: **в момент прохождения дедлайна** она автоматически создаёт клон себя со сдвинутым дедлайном, а сама становится «бесплодной». Клон в свой срок порождает следующий клон — и так далее, пока на активной задаче не нажат **Готово** (это обрывает цепочку). Каждый пройденный период остаётся как отдельная задача-напоминание.

Триггер — **прохождение дедлайна**, а не нажатие «Готово». Это сознательный выбор: кнопка завершения могла бы попасть на момент, когда период повтора прошёл уже несколько раз, и тогда непонятно, сколько клонов создавать. Привязка к дедлайну делает каждый период самостоятельным.

---

## Что реализовано

- Правило повтора: **«Без повторения»**, **«Каждые 1..7 дней»** или **«По дням недели»** (один или несколько дней из Пн–Вс).
- Повтор доступен только для задач **с ответственным и дедлайном** (UI прячет пикер, если одно из двух не задано).
- В момент дедлайна на устройстве ответственного создаётся клон: новый `id`, `status = TODO`, `completedAt = null`, `dueDate += interval`, остальные поля (assignedTo, description, priority, **правило повтора**) наследуются.
- Catch-up: если устройство было выключено несколько периодов, при пробуждении доплождаются все пропущенные клоны разом — без лимита (каждый пропуск = отдельное напоминание).
- Иконка 🔁 на карточке задачи в списке, если повтор активен.

## Модель данных

Правило хранится **строкой** — `Recurrence.serialize()`:

| Правило | Строка |
|---|---|
| `Recurrence.None` | `"none"` |
| `Recurrence.EveryNDays(n)` | `"days:N"` (N = 1..7) |
| `Recurrence.Weekly(days)` | `"weekdays:mon,wed,sat"` (3-буквенные аббревиатуры через запятую, отсортированы по значению) |

- `domain/model/Recurrence.kt` — sealed-тип. Ключевой метод `nextDueDate(from: Long): Long?` инкапсулирует вычисление следующего дедлайна; движок зовёт **только его** и не знает, как устроено правило.
- `Task.recurrence: Recurrence` (доменный тип). В `TaskEntity` и `TaskDto` — строка `repeatRule` (маппинг через `Recurrence.parse()` / `.serialize()`), по образцу `status`/`priority`.
- **Схема БД: версия 3.** Миграция `MIGRATION_2_3` (`AppDatabase.kt`): `ALTER TABLE tasks ADD COLUMN repeatRule TEXT NOT NULL DEFAULT 'none'`.
- **Sync обратно совместим:** поле `repeatRule` в `TaskDto` имеет дефолт `"none"` — старый партнёр без этого поля десериализуется в `None`. Версия протокола не менялась.

## Движок — owner-only спавн

**Проблема:** триггер по дедлайну, а не по действию пользователя. Если бы оба устройства порождали клон в момент дедлайна — получилось бы два клона с разными `id` (дубликат).

**Решение:** клон порождает **только устройство ответственного** (`assignedTo == myDeviceId`). Напарнику это не нужно — он получает клон обычным `/sync`. Это полностью убирает распределённую дедупликацию: клон получает обычный случайный UUID, потому что его создаёт ровно одно устройство.

### Идемпотентность — «гашение родителя»

После спавна воркер ставит родителю `recurrence = None`. Это маркер «бесплоден» **без отдельного поля схемы**: если воркер запустится повторно (ретрай / устаревший enqueue), guard `recurrence != None` сделает no-op. Правило повтора всегда «живёт» ровно на одной задаче цепочки — самой свежей, ещё не прошедшей дедлайн.

### Поток

```
RecurrenceSpawnWorker (на момент dueDate, устройство ответственного)
  └─ перечитать задачу из БД
  └─ guard: !deleted && status != DONE && recurrence != None
            && dueDate != null && assignedTo == myDeviceId
            && dueDate == expectedDueDate   ← иначе no-op (устаревший воркер)
  └─ catch-up цикл, пока dueDate родителя <= now:
       • создать клон (новый id, dueDate = recurrence.nextDueDate(due))
       • погасить родителя (recurrence = None)
       • запланировать due-уведомления клона
       • родителем становится клон
  └─ финальному живому клону (dueDate в будущем) завести его spawn-воркер
```

### Планирование и отмена

`NotificationScheduler.scheduleRecurrenceSpawn(task)` / `cancelRecurrenceSpawn(taskId)` — по образцу due-уведомлений: `OneTimeWorkRequest` + `setInitialDelay(dueDate - now)`, тег `id + "_spawn"`, политика **REPLACE** (правка дедлайна/правила перепланирует). Вызовы из тех же мест, что и due-уведомления:

| Источник | Когда |
|---|---|
| `CreateTaskViewModel.save` | при создании задачи, назначенной на меня |
| `TaskDetailViewModel` (`cycleStatus`/`updateTask` → `applyDueNotificationState`, `delete`) | смена статуса/полей/удаление |
| `MergeTasksUseCase` | входящая новая/обновлённая задача, назначенная на меня (REPLACE подхватывает изменённый партнёром дедлайн/правило) |

Guard планирования везде один: `recurrence != None && dueDate != null && assignedTo == myDeviceId && status != DONE && !deleted`. Реальная защита — повторный guard внутри воркера на старте.

### Почему отдельный воркер, а не `DueNotificationWorker`

`DueNotificationWorker` — чисто презентационный (только `notify()`, без зависимостей от БД), стреляет **до** дедлайна (−1д/−1ч). Спавн стреляет **в момент** дедлайна, требует `TaskRepository` и пишет в БД. Разные данные, тег, тайминг → разные воркеры. Переиспользован только механизм (`OneTimeWorkRequest + setInitialDelay + @HiltWorker`).

## Известные ограничения

- **Повтор без ответственного невозможен.** Owner-only: без владельца некому спавнить. UI прячет пикер; даже если правило попадёт на неназначенную задачу, guard `assignedTo == myDeviceId` его не запустит (дремлет).
- **Оба офлайн завершили один повтор одновременно** → может возникнуть два клона. Тот же класс, что общий last-write-wins; для приложения на двоих приемлемо.
- **Узкая гонка при смене ответственного у самого дедлайна:** если устройства на миг разошлись в том, кто владелец, — теоретически двойной спавн или ни одного. Окно крошечное (assignee меняют редко).
- **Накопление без лимита.** Невыполненная просроченная задача остаётся, рядом появляется новая. При коротких периодах это много задач — сознательный выбор («календарь напоминаний», ответственность на пользователе).
- **Тайминг воркера** подчиняется WorkManager + Doze. Опоздание безвредно для корректности: воркер считает дедлайн от сохранённого `dueDate`, а не от `now`, и идемпотентен.

## Будущие изменения

Строковое правило + `Recurrence.nextDueDate()` выбраны именно ради расширения **без миграции схемы и без правок движка** (воркер/sync/owner-only/гашение — агностичны к виду правила). Достаточно нового подтипа `Recurrence`, ветки в `parse()`, своей реализации `nextDueDate()` и UI.

### Повтор в конкретный день (день недели) — **реализовано**

`Recurrence.Weekly(days: Set<DayOfWeek>)` — строка `"weekdays:mon,wed,sat"`. `nextDueDate(from)` ищет ближайший следующий день из набора (минимум +1 день, через `java.time`). Catch-up цикл в воркере отрабатывает чередование (Ср → Сб → Ср...) без изменений.

UI: `RecurrencePicker` расширен — в дропдауне появился пункт «По дням недели»; при его выборе под полем появляется строка `FilterChip` для каждого дня (Пн–Вс, `FlowRow`). Последний выбранный чип снять нельзя.

### Повтор на конкретное число месяца

- Новый подтип `MonthlyOnDay(day)` со строкой `"monthday:15"`.
- `nextDueDate(from)` через `Calendar`: следующий месяц с тем же числом (аккуратно с 28–31).
- Движок не меняется.

## Тесты (план, ещё не написаны)

Зафиксировано как TODO:

1. **`Recurrence.parse` / `serialize`** — round-trip для `None`, `EveryNDays(1..7)` и `Weekly`; некорректные строки (`"days:0"`, `"days:9"`, `"weekdays:"`, `"garbage"`, `null`) → `None`.
2. **`Recurrence.EveryNDays.nextDueDate`** — `from + N*сутки` для границ N = 1 и N = 7.
   **`Recurrence.Weekly.nextDueDate`** — сегодня Пн, дни {Ср,Сб} → +2; сегодня Сб → +4 (до Ср); один день в наборе = тот же день → +7.
3. **`RecurrenceSpawnWorker` (guard)** — no-op при `deleted` / `status == DONE` / `recurrence == None` / `assignedTo != myId` / `dueDate != expected`.
4. **`RecurrenceSpawnWorker` (спавн)** — один пройденный период → один клон с верным `dueDate`, родитель погашен (`recurrence == None`).
5. **`RecurrenceSpawnWorker` (catch-up)** — N пройденных периодов → N клонов, финальный с `dueDate > now`, ему заведён spawn-воркер.
6. **`RecurrenceSpawnWorker` (идемпотентность)** — повторный запуск на погашенном родителе → no-op, без второго клона.
7. **`MergeTasksUseCase`** — входящий клон от партнёра трактуется как обычная новая задача (`added`), второй спавн на стороне получателя не запускается.
8. **owner-only** — на устройстве, где `assignedTo != myDeviceId`, спавн не планируется и не выполняется.
