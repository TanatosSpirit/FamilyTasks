# Архитектура синхронизации FamilyTasks

Полное описание того, как два устройства находят друг друга и обмениваются задачами.

---

## Общая картина

В приложении **5 механизмов**, которые работают вместе:

```
┌─────────────────────────────────────────────────────────────┐
│                    SyncService (контейнер)                   │
│                                                             │
│   ┌─────────────────┐      ┌──────────────────────────┐    │
│   │  UdpDiscovery   │      │       HttpServer          │    │
│   │  (ищет партнёра)│      │  (принимает sync от него) │    │
│   └────────┬────────┘      └──────────────────────────┘    │
│            │ нашёл IP                                        │
│            ▼                                                 │
│   ┌─────────────────┐                                       │
│   │   triggerSync   │                                       │
│   │ (HttpClient →   │                                       │
│   │  POST /sync)    │                                       │
│   └─────────────────┘                                       │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│              WorkManager / SyncWorker (резерв)               │
│           запускается каждые ~15 мин независимо             │
└─────────────────────────────────────────────────────────────┘

┌──────────────┐    ┌──────────────────────────────────────┐
│ BootReceiver │    │           WifiReceiver                │
│ (старт после │    │  (должен триггерить sync при WiFi,   │
│  перезагруз.)│    │   но не работает на Android 8+)      │
└──────────────┘    └──────────────────────────────────────┘
```

Ключевая идея: `SyncService` — это основной "двигатель" синхронизации, который работает постоянно. `WorkManager` — страховка на случай если что-то пошло не так.

---

## Механизм 1 — SyncService (Foreground Service)

### Технически
`android.app.Service` с флагом `START_STICKY`, запущенный как Foreground Service. Содержит внутри себя оба компонента реального времени: `UdpDiscovery` и `HttpServer`. Работает в своём `CoroutineScope(SupervisorJob + Dispatchers.Default)`.

### Простым языком
Это процесс-контейнер, который Android обязан держать живым. Без него `HttpServer` и `UdpDiscovery` были бы убиты системой через несколько минут. Чтобы пользователь видел, что процесс работает — он показывает постоянное уведомление в шторке (без этого Android 9+ запрещает Foreground Service).

### Когда запускается
- При загрузке устройства (через `BootReceiver`)
- При запуске приложения (если не запущен)
- При получении `ACTION_SYNC_NOW` (от `WifiReceiver`, который де-факто не работает)

### Текущие параметры
- Флаг: `START_STICKY` — если Android убьёт сервис (нехватка памяти), он перезапустится автоматически
- Тип: `connectedDevice | dataSync` — обязательно для Android 14+
- Канал уведомления: `IMPORTANCE_LOW` (без звука и вибрации)

### Для чего нужен
**Кейс:** Вы добавили задачу. Партнёр в это время смотрит видео с выключенным экраном. Чтобы его устройство приняло вашу задачу — его `HttpServer` должен быть жив и слушать порт 8080. Без Foreground Service Android давно бы его убил.

### Ограничения
- Агрессивные прошивки (Xiaomi MIUI, Samsung с режимом экономии батареи) могут убивать Foreground Service даже с `START_STICKY`. Приложение перезапустится, но с задержкой.
- На Android 15 требования к Foreground Service ужесточаются.

## Механизм 2 — UdpDiscovery (поиск партнёра)

### Технически
Два параллельных корутина на `Dispatchers.IO`:
1. **Broadcast-корутин** — каждые 30 секунд создаёт `DatagramSocket`, отправляет UDP-пакет на `255.255.255.255:9090` и закрывает сокет
2. **Listen-корутин** — держит открытый `DatagramSocket` на порту `9090`, ждёт входящих пакетов

Пакет содержит: `{ deviceId, httpPort: 8080 }`.

`MulticastLock` захватывается при старте и держится, пока сервис жив — это разрешает WiFi-чипу не фильтровать broadcast-пакеты.

### Простым языком
Устройство периодически "кричит" в сеть: "Я здесь, мой ID такой-то, HTTP у меня на порту 8080". Второе устройство слушает и отвечает тем же. Как только один услышал другого — IP партнёра записывается в `SyncManager.peerIp` и немедленно запускается синхронизация.

### Когда срабатывает
- Сразу после старта `SyncService` — начинает слушать и рассылать
- При получении пакета от партнёра → вызывается `onPeerDiscovered(ip, deviceId)` → `triggerSync()`

### Текущие параметры
| Параметр | Значение |
|---|---|
| Порт | UDP 9090 |
| Адрес broadcast | `255.255.255.255` |
| Интервал broadcast | **30 секунд** |
| Размер пакета | 1024 байта (буфер приёма) |
| Фильтрация | принимает только от `pairedDeviceId` (или от любого, если сопряжения нет) |

### Для чего нужен
**Кейс:** Оба телефона приходят домой. Подключаются к одному WiFi. Оба начинают рассылать UDP. Через ≤30 секунд каждый слышит другого → оба запускают `triggerSync` → задачи синхронизируются.

**Кейс:** Один телефон был выключен. Включился, подключился к WiFi → `SyncService` стартует → UDP-discovery → синхронизация. Всё автоматически, без действий пользователя.

### Ограничения
- UDP broadcast может быть заблокирован роутером (корпоративные сети, некоторые гостевые сети). Для домашнего роутера обычно работает.
- `MulticastLock` держится постоянно — это одна из причин расхода батареи (см. `improvements_plan.md`).
- Если оба устройства отправляют broadcast **одновременно** — оба одновременно вызывают `triggerSync`. Защита от двойного sync — проверка `syncState == SYNCING` в `triggerSync()`.

## Механизм 3 — HttpServer (приём входящего sync)

### Технически
`NanoHTTPD`-сервер, запущенный на порту `8080`. Обрабатывает единственный эндпоинт: `POST /sync`. Читает тело через `DataInputStream.readFully()` (важно — `InputStream.read()` не гарантирует чтение всех байт за один вызов). Вызывает `onSyncRequest` — лямбду, переданную из `SyncService`, внутри `runBlocking`.

### Простым языком
Это "входная дверь" для синхронизации. Партнёр стучится сюда со своим списком задач. В ответ — получает ваш список. Оба мерджат полученное в свою базу.

### Когда срабатывает
Только когда **партнёр** инициирует sync — отправляет POST на ваш порт 8080. Вы сами ничего не делаете — просто отвечаете.

### Текущие параметры
| Параметр | Значение |
|---|---|
| Порт | TCP 8080 |
| Протокол | HTTP (plain, не HTTPS) |
| Метод | только POST /sync |
| Формат | JSON (`SyncPayload`) |

### Для чего нужен
**Кейс:** Ваше устройство в спящем режиме, `peerIp` не определён (вы ещё не слали UDP). Партнёр вас нашёл по UDP и инициирует sync. Ваш `HttpServer` жив (Foreground Service), получает запрос, мерджит задачи партнёра, отвечает своими. Синхронизация произошла, даже если вы были "пассивной" стороной.

### Ограничения
- Нет аутентификации. Любое устройство в той же WiFi-сети может отправить POST /sync и получить все ваши задачи или внедрить фейковые. (Актуально только в недоверенных сетях.)
- `NanoHTTPD` однопоточный по умолчанию. Одновременно обрабатывается один запрос. Для 2 устройств это не проблема.

## Механизм 4 — triggerSync / HttpClient (инициирование sync)

### Технически
`triggerSync()` — метод в `SyncService`. Проверяет: есть ли `peerIp` и не идёт ли уже sync (`syncState != SYNCING`). Если всё ок — запускает корутину, которая:
1. Читает все задачи из базы (`getLocalSnapshot()`)
2. Собирает `SyncPayload`
3. Вызывает `HttpClient.sync(peerIp, 8080, payload)` — POST запрос с таймаутом connect 5с / read 10с
4. Если ответ получен — запускает `MergeTasksUseCase` на пришедших задачах
5. Обновляет `lastSyncAt` и `syncState`

`SyncWorker` делает то же самое, но запускается от WorkManager, а не от события.

### Простым языком
Это "активная" синхронизация — вы сами идёте к партнёру. Отправляете ему все свои задачи, получаете все его, мерджите.

### Когда вызывается
- Из `UdpDiscovery.onPeerDiscovered` — сразу после обнаружения IP партнёра
- Из `SyncService.onStartCommand` при получении `ACTION_SYNC_NOW` (от `WifiReceiver`, который не работает)
- Из `SyncWorker.doWork()` — по расписанию WorkManager

### Текущие параметры
| Параметр | Значение |
|---|---|
| Таймаут подключения | **5 секунд** |
| Таймаут чтения | **10 секунд** |
| Защита от параллельных вызовов | проверка `syncState == SYNCING` |
| При ошибке | `syncState = ERROR`, без retry (retry берёт на себя WorkManager) |

### Для чего нужен
**Кейс:** Вы обнаружили партнёра через UDP. Надо немедленно синхронизироваться, не дожидаясь следующего цикла WorkManager (который произойдёт через 15 минут).

### Ограничения
- Если `peerIp` устарел (партнёр сменил IP, ушёл из сети) — `HttpClient` получит таймаут через 5 секунд. После этого `syncState = ERROR`. Новый IP партнёра придёт только с его следующим UDP-пакетом.
- Нет retry при ошибке сети — кроме WorkManager. Если sync не прошёл, следующая попытка не раньше чем через ~15 минут.

## Механизм 5 — WorkManager / SyncWorker (периодический резерв)

### Технически
`PeriodicWorkRequestBuilder<SyncWorker>(5, TimeUnit.MINUTES)` с политикой `KEEP` (не пересоздавать, если уже запланирован). WorkManager выполняет задачу с учётом системных ограничений (Doze Mode, App Standby). `SyncWorker` — `CoroutineWorker` с `@HiltWorker`.

### Простым языком
Независимый будильник, который говорит: "Каждые N минут попробуй синхронизироваться". Работает даже если UDP-discovery ничего не нашёл. Работает даже если приложение закрыто (WorkManager — системный планировщик, не зависит от жизни процесса).

### Когда запускается
- Автоматически по расписанию, примерно каждые 15–20 минут
- Планируется при старте приложения (`FamilyTasksApplication.onCreate()`)

### Текущие параметры
| Параметр | Значение |
|---|---|
| Указанный интервал в коде | 5 минут |
| Реальный минимум WorkManager | **15 минут** (библиотека принудительно заменяет всё меньшее) |
| Политика при дублировании | `KEEP` — если задача уже есть, новая не создаётся |
| Retry при ошибке | `Result.retry()` — WorkManager попробует снова с экспоненциальной задержкой |
| При отсутствии `peerIp` | немедленный выход (`Result.success()`), никакой сети не трогает |

### Для чего нужен
**Кейс:** Оба устройства долго в одной сети. UDP работает нормально. Но представьте: на одном устройстве роутер заблокировал broadcast (гостевая сеть, VPN). UDP не работает, IP партнёра так и не получен. WorkManager раз в 15 минут пробует sync — но `peerIp == null`, сразу выходит. Sync не произойдёт.

**Кейс где он реально помогает:** `peerIp` был получен давно через UDP, IP не изменился, но UDP-пакеты временно не доходили (помехи, краткий обрыв). WorkManager использует закешированный `peerIp` и успешно синхронизирует.

### Ограничения
- Если `peerIp == null` — SyncWorker ничего не делает. WorkManager сам по себе не умеет находить партнёра.
- В режиме Doze (экран выключен, не заряжается, устройство неподвижно) WorkManager откладывает задачи до следующего "окна активности". Реальный интервал может быть значительно больше 15 минут.
- Не гарантирует точное расписание — это осознанное решение Android (батарея важнее точности).

## Механизм 6 — BootReceiver (старт после перезагрузки)

### Технически
`BroadcastReceiver` на `Intent.ACTION_BOOT_COMPLETED`. Вызывает `ContextCompat.startForegroundService(SyncService)`.

### Простым языком
Когда телефон перезагрузился — приложение не запущено, `SyncService` не работает. `BootReceiver` автоматически его запускает, не требуя открыть приложение.

### Ограничения
- На некоторых прошивках (Xiaomi, Huawei) требует явного разрешения "Автозапуск" в настройках системы.
- Доставляется с задержкой после загрузки (система сначала запускает критичные процессы).

## Механизм 7 — WifiReceiver (фактически не работает)

### Технически
`BroadcastReceiver` на `WifiManager.WIFI_STATE_CHANGED_ACTION`, зарегистрированный в `AndroidManifest.xml`.

### Проблема
Android 8.0 (API 26) — это ваш `minSdk`. Начиная с Android 8.0 система **не доставляет** implicit broadcasts манифест-ресиверам. `WIFI_STATE_CHANGED` входит в этот список. Ресивер зарегистрирован, но никогда не вызывается.

### Что это значит
Задумывалось: WiFi включился → `WifiReceiver` → `ACTION_SYNC_NOW` → немедленный sync. На практике: это не работает ни на одном устройстве в вашем minSdk диапазоне.

### Нужен ли он вообще
Нет. Можно удалить. UDP-discovery всё равно обнаружит партнёра в течение ≤30 секунд после подключения к сети.

## Механизм мерджа — MergeTasksUseCase

### Технически
Получает список `remoteTasks`. Загружает все локальные задачи в `Map<id, Task>`. Для каждой remote-задачи:
- нет локальной → добавить
- есть локальная, `remote.updatedAt > local.updatedAt` → заменить
- `updatedAt` одинаковый → оставить локальную (tie-break)

Затем `upsertTasks(merged)` — записать весь результат в Room.

### Простым языком
Побеждает тот, кто сохранил задачу **позже**. Время сохранения — это `updatedAt` (Unix timestamp в миллисекундах).

### Важное про удаление
Удаление задачи — не физическое. Устанавливается флаг `deleted = true` и обновляется `updatedAt`. Merge подчиняется тому же правилу: если remote-задача `deleted = true` с более новым `updatedAt` — она "победит" и задача исчезнет из UI (но останется в базе).

## Полный порядок событий

### Нормальный сценарий: оба телефона приходят домой

```
Устройство A                          Устройство B
     │                                      │
     │  [Подключились к WiFi]               │
     │                                      │
     │──── UDP broadcast ──────────────────►│ (≤30 сек)
     │◄─── UDP broadcast ───────────────────│
     │                                      │
     │  onPeerDiscovered(ipB)               │  onPeerDiscovered(ipA)
     │  syncManager.setPeerIp(ipB)          │  syncManager.setPeerIp(ipA)
     │  triggerSync()                       │  triggerSync()
     │                                      │
     │──── POST /sync (все задачи A) ──────►│
     │    HttpServer B обрабатывает         │
     │    mergeAll(задачи A)                │
     │◄─── ответ (все задачи B) ────────────│
     │                                      │
     │  mergeAll(задачи B)                  │
     │                                      │
     │  [Обе базы синхронизированы]         │
```

### Сценарий: одно устройство долго было офлайн

```
Устройство A (было офлайн)            Устройство B (работало)
     │                                      │
     │  [A включается, подключается к WiFi] │
     │  BootReceiver → SyncService стартует │
     │  UdpDiscovery начинает broadcast     │
     │                                      │
     │──── UDP broadcast ──────────────────►│
     │◄─── UDP broadcast ───────────────────│
     │                                      │
     │  [triggerSync на обоих]              │
     │  [Полный обмен всеми задачами]       │
     │  [Merge: побеждает более новый updatedAt] │
```

### Сценарий: UDP не работает (заблокирован роутером)

```
     │  [peerIp не определён никогда]
     │
     │  WorkManager каждые ~15 мин:
     │  SyncWorker.doWork()
     │  peerIp == null → Result.success() → ничего не происходит
     │
     │  [Синхронизация невозможна без ручного ввода IP]
```

## Нужен ли каждый механизм вашему приложению

| Механизм | Нужен? | Комментарий |
|---|---|---|
| SyncService | ✅ Да | Без него HttpServer мёртв — пассивная синхронизация невозможна |
| UdpDiscovery | ✅ Да | Единственный способ автоматически найти партнёра без сервера |
| HttpServer | ✅ Да | Принимает входящие sync. Без него устройство только инициирует, но не принимает |
| triggerSync / HttpClient | ✅ Да | Активная синхронизация сразу после обнаружения партнёра |
| WorkManager / SyncWorker | ✅ Да (как страховка) | Нужен на случай временных проблем с UDP или если `peerIp` кешируется |
| BootReceiver | ✅ Да | Без него нужно открывать приложение после каждой перезагрузки |
| WifiReceiver | ❌ Нет | Не работает на Android 8+. Можно удалить без последствий |
| MergeTasksUseCase | ✅ Да | Сердце логики синхронизации |

## Статусная строка на главном экране

Под названием приложения отображается строка, отражающая текущее состояние синхронизации. Логика — `syncStatusText()` в `TaskListScreen.kt:279`.

Состояния проверяются в порядке приоритета сверху вниз:

| Что показывает | Условие | Что это значит |
|---|---|---|
| **Нет подключения к Wi-Fi** | `wifiConnected == false` | WiFi и Ethernet не подключены. Синхронизация невозможна в принципе — WorkManager не запускает SyncWorker, UDP-пакеты некуда слать |
| **Офлайн** | `peerIp == null` | WiFi есть, но UDP-discovery ещё не получил пакетов от партнёра. Второй телефон не в сети, не в той же WiFi, или UDP заблокирован |
| **Синхронизация...** | `syncState == SYNCING` | Прямо сейчас идёт HTTP-обмен с партнёром |
| **Ошибка синхронизации** | `syncState == ERROR` | HTTP-запрос к партнёру завершился ошибкой (таймаут, недоступен) |
| **Онлайн** | `peerIp != null`, sync ни разу не проходил | Партнёр виден в сети, но успешного обмена ещё не было |
| **Синхр. N мин назад** | `peerIp != null`, `lastSyncAt > 0` | Нормальное рабочее состояние |

**Важно:** "Офлайн" — не признак поломки. Это просто означает что `peerIp == null`, то есть UDP-discovery не получал пакетов от партнёра. Как только партнёр появится в сети и придёт UDP-пакет — статус сменится автоматически.

**`peerIp` не сбрасывается** при потере связи — он хранится в `SyncManager` в памяти и живёт до перезапуска сервиса. Поэтому после первого обнаружения партнёра "Офлайн" не вернётся, даже если партнёр ушёл из сети — до перезагрузки приложения.
